Try it

This is a clickable model of the new homework screens, built with the app's own colours, fonts, icons and characters. Click anything: cards, rows, buttons, tabs, the chat box, the settings icon. It behaves like the app will. Press Start and Dot works through its steps, then hands you the result to check.

Three paths to try:

  1. Open HW 12 from the week, click I've signed in, and watch Dot finish.
  2. Open exercise_11, settle the two notes, then hand it in. Switch the rule above to see how the ending changes.
  3. Click the chat box on the week and try each suggestion.

Screens

Every screen starts from two questions: what is the student thinking when they land here, and what is the one thing they'll do next? The answer to the first goes at the top in plain words. The answer to the second is the one yellow button. Everything else is there to back those up, or it goes.

The assignment page

The page works like Codex or Claude Code: the agent on the left, what it's working on at the right.

  • Left: Dot's turns. Dot writes a short plan, then each action shows as a tool call: an icon, a verb, the target in monospace, and the result ("Ran make test · 12 passed", "Opened webassign.net/…", "Edited sort.c · +48 −3"). The call Dot is on pulses. When Dot finishes, the calls fold into "Worked for 6m 12s · 7 steps". Your messages and Dot's replies continue in the same thread, and saved memories show inline with Undo.
  • Your move. When Dot needs you, a yellow prompt sits above the chat box, like an agent asking for approval. It holds the one decision and its buttons: sign in, answer a question, settle two doubts and hand it in. When nothing is needed, there's no prompt, and the send button becomes Stop while Dot works.
  • Right: what Dot is working on. The school page or vendor site in a small browser frame with its address, marked "Dot is using this page" with Take over. The work (answers, draft or files) is another tab. Details holds the due date, class, what the school says, the rule, the late policy and where Dot found it. The right tab opens by itself for each state.
  • Header. The title, class and due date. Whose turn it is shows in the page itself, not as a status label.

The UI polish

  • Short class codes. There's no short-code field; CourseSchema only has label. Derive "CSC 316" from the label.
  • Colours that don't collide. Today a class's colour is the sum of its label's letter codes, mod 6 (assignmentPresentation.ts:18), so two classes can share one. Give classes colours in order.
  • One set of words. Today one rule has three names. From now on it's Leave it to me, Do it, I'll hand it in and Do it and hand it in everywhere.
  • Hierarchy. One yellow button per screen, a quiet fill for second actions, and links only inside sentences. Shantell Sans is only for Dot's voice.
  • Motion. The chat grows in 200 ms, cards lift on hover, and Dot blends between states. All of it respects reduced motion.
  • Pushed updates instead of polling. The chat polls every 0.65–1.2 s today (ChatWorkspace.tsx:208).
  • Remove dead code: DeskDrawer (imported, never rendered), boardView, weekOffset, AssignmentCard, the add-homework form, and the old CSS these screens replace.

Rules: how they work, and do they work?

How they work today

  • There are three choices (shared/permission.ts:11):
    • leave it (do_not_attempt);
    • do it, I hand in (attempt);
    • do it and hand in (auto_submit).
    With no rule at all, Dot leaves the work alone.
  • A rule can cover all homework, one class, one kind of work in a class, or one assignment. The most specific wins: assignment, then kind, then class, then all (permission.ts:121).
  • Three things force "leave it" whatever the rules say: "I'll do it myself", an ignored assignment, and a class that merged badly (manager/coordinator.ts:473-483).
  • Do it, I hand in: Dot stops at "Ready for you". You hand it in on the school page and type the confirmation you see, and Dot checks the page says so (assignment/coordinator.ts:233).
  • Do it and hand in: after your review time, Dot hands it in. It only does this if it has no doubts, the schedule isn't paused and Studi is open (:299-304). Otherwise it saves the answer.

Do they work? The audit

Mostly yes:

  • Every start and every hand-in re-checks the current rule.
  • Dot can't use the hand-in tool without your click or the rule's timer, and chat can't trigger it.
  • The permission and lifecycle tests all pass: 45 of 45, run against today's build.

Start→ are the details fresh?take the school page→Pi session, shared with the assignment's chat→tools: school page, files, terminal, documents, tell the student→record answers → Ready for you→hand in: rule timer or your click

At the start, Dot gets:

  • the assignment;
  • the rule;
  • notes about the class and the assignment;
  • the last receipt;
  • the folder listing;
  • a snapshot of the page (assignment/coordinator.ts:355-389).

Icon and characters

  • Live icon badge (electron/app-status.ts):
    • needs you: a coral "!" and one taskbar flash;
    • ready to check: a green count;
    • working or scanning: a pencil or magnifier, plus a progress bar;
    • otherwise: the plain S.
    The Mac Dock and the tray show the same status.
  • Characters: Dot is on every homework surface, including the school-page overlay. It's drawn once (shared/characters/rig.ts) and moved by a small controller (characterMotion.ts):
    • each state holds for at least 600 ms, and the latest request wins;
    • loops blend instead of snapping;
    • off-screen characters rest;
    • the eyes follow the pointer;
    • with reduced motion on, it shows still poses.
  • States: dotState() replaces deskInkyState and adds review for "Ready for you". The same function drives the icon badge. All 20 <Inky> call sites move to <Character>, then shared/inky.ts and its CSS are deleted.
  • Name: homework copy and the agent packs say Dot (packs/core/inky → packs/core/dot). Stored field names stay the same, so no migration is needed.
  • Already started (uncommitted): the icon files, the rig, the motion controller, Character.tsx, states.ts and a preview sheet.

Staying signed in

  • Why sign-ins are lost: school pages use the saved session persist:studi-school (main.ts:1059). But Chromium drops cookies with no expiry date when the app quits, and single sign-on often uses exactly those. Nothing in Studi keeps them.
  • Keep them:
    • save the school's session cookies on quit and every 10 minutes, encrypted with safeStorage;
    • restore them on launch, before any school page loads;
    • drop them after 14 days;
    • delete the file on sign-out or when the device is released.
  • Keep the session alive while Studi runs in the tray and the computer is awake:
    • Moodle: core_session_time_remaining, then core_session_touch. Both are already allowed as read-only (read-only-guard.ts:10).
    • Canvas: a read-only GET.
    • Anything else: load the school's root page every 20 minutes.
  • Remind once: "If your school asks, tick 'remember this device'." It shows on the sign-in step and on "Needs you: sign in". Studi never types or ticks anything itself.
  • When the school signs you out:
    • you get one notification, never repeated for the same sign-out;
    • work that needs the school page waits, and everything else carries on;
    • once you sign in, the waiting work carries on by itself.
    Today the whole scan stops (scan/coordinator.ts:1727).

How testing works

Studi has four kinds of test. Each proves something different, and only the last two use a real model.

1. Quick checksbun run verify --changed

Typecheck plus unit tests for the parts you changed: rules, storage, tools, screen logic. No app window, no model, about a minute.

It proves the pieces are right, not that Dot can do homework.

2. The fake schoolbun run lms -- start --scenario quiz

A pretend school website on your machine (agent-harness/lms). It can look like Moodle, Canvas or an unknown school site. It has a WebAssign-like site, a Duo-style sign-in, 22 made-up semesters, and a hidden answer key Studi never sees. Faults can be triggered mid-run: sign-outs, moved deadlines, failed downloads.

It's the stage. On its own it tests nothing.

3. Scan benchmarkbun run benchmark -- live --scenario moodle-noisy

Starts the fake school, runs Studi's real scan engine with GPT-6 Sol in a hidden window, then grades what it saved against the answer key: found, dates, statuses, junk, time and tokens.

It covers scans only. Nothing grades homework this way yet.

4. Homework runsbun run test:e2e · tests/live

e2e: the whole app on the fake school with a scripted model that gives fixed replies. It proves the plumbing: stop at review, hand in once, takeover, stop. live: a real model on 2 tasks, pass or fail, run by hand.

Just one quiz and one coding task, with no scores or comparison.

PostHog: record everything

The private beta is you and one friend, so everything is recorded, with no consent step. Replay and events are already on by default, with full text (telemetry/service.ts:520, renderer.ts:57). What's missing:

  • An event for every Dot step in scans and homework (tool, duration, outcome, page URL and title), every error with its assignment or scan, and cost per turn in dollars.
  • Rule changes, memory writes, hand-ins, and every change in an assignment's state.
  • The school page: it runs in its own view, so replay can't see it. Attach a screenshot of it to each hand-off, error and hand-in.
  • Each person identified by their Studi account, so the two of you can be told apart. Each replay is linked to the scan or assignment it shows.
  • Passwords and sign-in codes stay hidden, as you asked before. Today only the provider sign-in code is marked data-secret (Ui.tsx:189); every code field gets it.

Order of work

  1. Measure first. Fix the scanDepth bug. Add homework-mix, the homework benchmark, the fault schedule and the scorecard. Record today's baseline.
  2. PostHog events for every step, error and cost, so real use is visible from day one.
  3. Rules fixes. Finding 1 first (small and high), then 2–9, each with a test.
  4. Make Dot reliable: one start, keep going, the watchdog, carrying on after a restart, kept error reasons, the method and the context. Then memory reading and writing. Measure again.
  5. One record per assignment, with pushed updates.
  6. Icon and characters: finish what's started, swap every call site, rename to Dot, then the live icon.
  7. Screens: the assignment page and chat first, then week, list, All, rules and memory, as in the prototype, checked in the preview at 1120 and 800 px.
  8. Staying signed in, measured with the new faults.
  9. Real assignments, read-only (the file-based ones in your folder), then your full test.

Each step ends with bun run verify --changed, the scorecard where Dot's behaviour changed, preview screenshots where screens changed, and a commit.

Decisions

  1. Dot everywhere, including the loading and update screens (recommended), or keep blue Inky there?
  2. Should Dot start by itself for "Do it, I'll hand it in" work? I recommend yes, because handing in still waits for you.
  3. Web access for Dot (programming docs, formulas)? It would help code and maths work. This is your call on academic integrity.
  4. Saved sign-in cookies: 14 days, or until the school's own expiry?
  5. The icon and character code I've started: keep it as the start of step 6 (recommended), or remove it?
