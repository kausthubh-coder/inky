Studi build plan

Turn the three Codex automations that already work for the student into one polished desktop app. Scanning finds the work. Inky does the homework. Inky tutors from the real course material. Each step below ends in a checkpoint with tests that must pass. When every checkpoint passes, the app works.

Written 2026-09-23 for the build agent. Branch t3code/learn-redo at 0c5ec3f. Repo root: C:/Users/kaust/.t3/worktrees/studi-2/t3code-7b59ae23. Companion docs: docs/redesign/scan-plan.html, learn-plan.html, learn-concept.html, concept.html, SPEC.md.

1. How the build agent works through this

  1. One branch. Work only on t3code/learn-redo in this worktree. Create no other worktrees or branches. Commit after each task with a clear message. Never use bare git stash. Don't push unless told to.
  2. Checkpoints are gates. Do the checkpoints in order. Finish a checkpoint by writing docs/reports/checkpoint-NN.md (format in section 9), committing it, and stopping. A reviewer reads the report and answers "approved" or sends a list of fixes. Don't start the next checkpoint before approval.
  3. Evidence, not claims. Each report pastes the exact commands and the tail of their real output, the metrics, and the screenshot paths. A claim without output counts as not done. If something fails or was skipped, say so plainly.
  4. Code quality. Write minimal, readable code that matches the surrounding style. Delete code the new design makes dead. Add no speculative abstractions. Add tests only where they guard real behaviour. Keep stored records backward compatible: add fields with zod defaults, because real users have SQLite data.
  5. Before touching any UI, read docs/redesign/SPEC.md section 8 (the visual system) and section 4 here. No sidebars, no pills, no busy cards. Each screen has one filled lead action.
  6. Safety. Never submit, post or enrol on a real school site during testing. Live runs against real schools are read-only scans only, and only in checkpoint 8.

Definition of done: three journeys

#JourneyPasses when
J1Sign in, then onboarding, then the first school check, then TodayEvery assignment due in the window shows on Today with the right class, title, due date and time (school time zone), status and link. Nothing extra: no slides, files or grade rows. Sign-in blockers are listed per system. The check finishes within its time target.
J2Start an assignment, Inky works it, review, submit (by rule or by the student), receiptThe school records exactly one submission with the right answers or files. The receipt matches it. Takeover and Stop work mid-run. Under "do it, I submit", nothing is submitted.
J3Add an exam or find it, then Learn page, then a tutor session, then the level changesThe goal comes from the real syllabus and study guide. Questions cite that material. The student's own unaided answers move the level at most one step. A study page renders. Progress persists across restarts.

Each journey runs automatically in three places: (a) scripted, against the fake school, on every commit; (b) live-model, against the fake school, nightly and before release; (c) read-only, against a real Moodle or Canvas account, before release (J1 only, plus J2 up to review).

5. Architecture decisions

5.1 Scan = the Codex automation, made structured

  • Prompt. Rewrite desktop/agent-system/packs/roles/scan/instructions.md and capabilities/scan-record/instructions.md around the automation's structure. (1) Sign-in preflight: classify each system as signed in, needs sign-in, denied, network, or down, and continue with what's reachable. (2) Discover from the dashboard timeline and calendar, then course pages, then linked systems. (3) Strictly read-only (copy the automation's read-only paragraph). (4) Report what couldn't be checked. Keep it under 60 lines. Studi supplies the school root, known courses, the previous run's rows and today's date.
  • Tools. Replace the 15 scan tools with 6:
    • scan_status: returns counts and what's left.
    • scan_record_system {system, url, state}
    • scan_record_course
    • scan_record_rows {courseKey, rows:[{title, href, dueText, statusText, kind, instructions?}]}: a row captured from one list item is its own evidence.
    • scan_record_source: a syllabus or study guide URL plus its text, for Learn.
    • scan_request_handoff
    The app, not the agent, finishes the scan when every course has rows or is marked blocked. Delete inventories, scan_check_source, scan_read_assignment and scan_finish, along with the evidence code that only they use.
  • Limits. A 30-minute active ceiling. Stop after 5 minutes with no new row or finished course. Three identical rejections skip that target. "Finish with what you found" stops within 5 s. There is no mid-run session restart. Tool results stay small ({saved, ids}).
  • Connectors first. Before the agent runs, detect Moodle or Canvas from the page. Call the school's own APIs from inside the signed-in page (webContents.executeJavaScript(fetch(...))):
    • Moodle: core_calendar_get_action_events_by_timesort and core_course_get_enrolled_courses_by_timeline_classification, with the calendar iCal as fallback.
    • Canvas: /api/v1/planner/items, /courses and /courses/:id/assignments (strip the while(1); prefix).
    Save those rows directly. The agent then only fills gaps: linked systems, and courses with no rows.
  • Dates. One parser, desktop/shared/due-date.ts, used by scan, Homework and Learn:
    • Dates are in the school's time zone.
    • A missing year means the current academic year, rolled forward if more than 6 months past.
    • A date with no time isn't overdue until the day ends.
    • Never invent a date; relative text like "Friday" is resolved against the page's capture date, or left unknown.
  • Identity and edits. Row identity is the Moodle cmid or Canvas assignment id, else the normalised URL. A field the student edited (for example dueDateOverride) is never overwritten. If the school changes that field, show one "the school changed this" notice.
  • Model. Scans run at low effort (a per-role setting in agent-runtime.ts). Homework and the tutor keep the student's chosen effort.

5.2 Browser layer

  • Stable refs. Map each ref to its backendNodeId. Reset refs only on a real main-frame navigation. Record tools never re-snapshot.
  • Small action results. Actions return {status: completed|failed|unknown, url, title, changed}. browser_snapshot takes {ref?, selector?, depth?, mode: full|diff}. Keep the last two snapshots verbatim in the context and replace older ones with a one-line stub.
  • browser_rows. A new tool that pages through a repeating list inside the page and returns compact rows. This removes one-visit-per-item.
  • Frames. Get the frame tree (Page.getFrameTree), read accessibility per frame, and prefix refs with the frame. Report frames it can't read instead of showing them blank.
  • Documents. One read_document tool for a link or download: follow Moodle's resource/view.php redirect, handle forced attachments, and use page images when a PDF has no text layer.
  • Read-only by enforcement, not labels. Delete the label guard at controller.ts:257. During scans, block non-GET form submissions and fetch/XHR requests with non-GET methods at the session level (session.webRequest.onBeforeRequest for the school partition). Allow a named list of exceptions: SSO or sign-in hosts, LTI launch POSTs, and the Moodle service.php read-only methods the connector calls. Scans also never receive browser_submit or browser_upload.
  • Fix the small bugs listed in section 3.

5.3 Homework = "do this assignment" thread

  • Keep assignment/coordinator.ts (phases, review, receipts, takeover). Simplify its prompt to the Codex thread's shape: the assignment row, its link, the instructions if the scan has them, the homework folder, the rule, and "open it, read everything including attachments, do the work, fill in the answers, then call assignment_start_review. Submit only if the rule allows."
  • assignment_start_review records doubts as {where, why} (SPEC section 4). The panel shows doubts first.
  • Add a label to every tool result ("Typed the answer to question 2") for the activity feed. The renderer never shows raw tool calls.
  • When the student opens or starts an assignment, a details scan reads instructions, attachments and the rubric for that one item.

5.4 Tutor = the CSC316 folder, inside Studi

  • Goal workspace. Each Learn goal gets a folder under the homework root: Learn/<class> <exam>/. It holds:
    • CONTEXT.md: goal, date, scope note, sources.
    • PROGRESS.md: evidence, gaps and the next target, rewritten by the tutor at wrap-up.
    • CHEATSHEET.md
    • sources/: extracted text of the syllabus, study guide and stems.
    • pages/: study pages.
    The tutor reads these at session start, the same way the CSC316 AGENTS.md bootstrap works. The SQLite mastery records stay the authority for levels.
  • Teaching rules. Merge the "How to teach", "Orient before questioning", "Respond to reasoning", "Diagnose confusion" and "Make visuals teach something specific" sections of C:/Users/kaust/Documents/CSC316-Exam1/AGENTS.md into TUTOR_SYSTEM_PROMPT (desktop/electron/agent/tutor-tools.ts). Remove anything specific to CSC316.
  • Study pages. Add a tutor_show_page {title, html} tool. The HTML renders in a sandboxed iframe: sandbox="allow-scripts", no same-origin, a CSP with default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline', no network. The page reports interactions back through postMessage as {explored:[…]}, which becomes the tool result. Pages are saved to pages/ so the student can reopen them. Keep the five built-in models as fast paths.
  • Grading stays in the app. Choice and typed answers are checked by the app. Explanations are graded against a rubric written before the answer. Only answers from Check and On your own count, and a level moves at most one step per session. This is already implemented; verify it.
  • Finding material. A "materials" scan kind (step 5.1) collects syllabi, study guides, past quizzes and slides for one class, and saves them as goal-attached sources.

8. Real schools: how to test safely

  1. Only the student's own accounts. Run with the student present for the first run.
  2. Always attach the scan-mode read-only guard, and save its log (blocked and allowed requests) to docs/reports/live/<date>-guard.log.
  3. Run the Codex automation the same morning. Compare its report with Studi's rows in a table: matched, missed by Studi, extra in Studi, date differs.
  4. If any real page confused the scanner, record it (sanitised) into the golden recordings and add its expected rows. Then the fake school catches it next time.
  5. Homework on a real school: stop at review only (the answers are filled but not submitted), under "do it, I submit". Submitting to a real school needs the student's explicit go-ahead in chat for that assignment.
