How Inky does homework

Its method (the prompt)

A short role written for any class and any site, like the school check's. No per-school rules.

  1. Understand. Read the instructions, rubric, attached files, the class note and related material. Work out every requirement.
  2. Decide where the work lives. On the school page (a quiz or form), in files (code, essay, report), or somewhere else (a vendor site, a repo).
  3. Do it, the way the class expects (from the class note and your saved preferences).
  4. Check it. Run the code and tests, redo the maths, go through the rubric line by line.
  5. Put it where it goes, without submitting unless your rule allows it.
  6. Hand it to you with proof for each requirement, and say what it isn't sure about.

Plus: tell or ask you only when it must, tools are shortcuts with the browser as backup, and the safety rules.

What it's told at the start (the brief)

  • The assignment: title, due date, school status, instructions, requirements
  • New: the class name and class note (grading, where work is handed in, your section)
  • New: how your school works (from the school check)
  • New: the class's saved materials and exams, and related assignments with their status
  • Your rule, your preferences, notes about this kind of work, and files already in the folder

What it can do (tools)

School pageRead, click, type, choose, scroll, screenshot. A plain click can never submit.
FilesRead, write and search its own folder for this assignment. Download from school, upload to school (never submits).
Run thingsA restricted terminal in that folder: compile, run tests, run Python or MATLAB-style scripts.
Read documentsPDFs and school pages, whole documents at once.
New: class materialsRead and search the class's saved syllabus, study guides and past work.
Talk to youTell you something, or ask and wait (a question, a sign-in, a file).
New: rememberSave a note at any time, plus an automatic "what I learned" note at the end of every run, including failed ones.
Hand-offReady for review with proof per requirement. Submit only when your rule allows, once, and only with new proof on the page afterwards.
Connected appsGoogle Docs, GitHub and others you've linked.

Removed: the separate "recovery plan" tool and instructions for tools Inky doesn't have.

State and sessions

One record per piece of work

Not started→Working⇄Waiting for you→Ready→Handed in

or Stopped, with the reason and the saved answer

  • The record holds the state, what Inky needs (if waiting), its session, the answer, the review and the receipt.
  • "Who has the browser" is simply whichever work is live. No separate lock record.
  • What the school says (submitted, graded) stays on the assignment. The screen shows both: "School: graded 10/10" and Inky's state.
  • The engine tells the screen when a record changes. The screen doesn't ask every second.

One session per piece of work

  • Inky's work and your chat about that assignment are one saved session, so nothing is lost between them, even after a restart.
  • Inky keeps going until it records a result. If the model stops early, Studi nudges it to continue up to 3 times, then asks you.
  • A watchdog stops it if it goes quiet or runs too long (like the school check).
  • After a crash, the work goes to "waiting for you". A submit is never repeated.

Starting

  • Button, chat and schedule all use the same start.
  • Your own Start isn't blocked by old or missing details. Inky re-reads the assignment itself first.
  • Automatic starts stay strict: fresh details and a rule that allows it.
Is checking permission 4 times good? No, it's more than needed. Two checks are enough: when work starts, and right before a submit, which is the only step that can't be undone. If you change a rule mid-way, Studi stops the live work straight away instead of re-checking on every tool call.

Design rules we follow

  • One thing leads. One filled button per screen; others are quieter (soft fill, text link, menu).
  • Say it once. Status appears in one place. No repeated headers or notes.
  • Show more only when asked. Requirements, history and settings open on demand.
  • No slop. No sidebars, pills, tinted cards, cards in cards or gradients. Hairlines and spacing do the grouping.
  • Plain words. "Waiting for you: sign in to WebAssign", not a state name.
  • Errors where they happen, next to the thing that failed.
  • Empty screens give one next step.
  • Frequent things are instant. Hovers and tab switches have no animation (craft: hover restraint).
  • Motion only for rare moments, 200 ms or less, easing out, and off when reduced motion is set. Inky's face changes are the one bit of delight.
  • Buttons press. A small scale-down on click.
  • Steady numbers. Dates, scores and counts use tabular figures.
  • Depth from soft shadows, not hard borders, for anything that floats.
  • Nested corners match: outer radius = inner radius + padding.
  • Big targets. Row actions and icons are easy to hit.

Sources: craft.gustavofior.com (hover restraint, tabular numbers, nested radius, novelty budget), and the baseline-ui, distill and taste guides.

Build order

  1. Measure. A homework test on the fake school with many kinds of work: quiz form, code with tests, essay with rubric, file upload, vendor site, repo, and one Inky can't do. Today nothing measures whether homework is done well.
  2. Inky. Method, brief, class materials reader, keep-going, watchdog, memory. Measure again.
  3. One start, with soft checks for your own starts, and the two permission checks.
  4. One work record, and the engine pushing changes to the screen.
  5. Screens on the new state: week, assignment page, chat. Build to these mockups, then compare screenshots.
  6. Real assignments, read-only: a few file-based ones prepared in your folder. Page-based work is tested only on the fake school, because a real site may save typed answers.
  7. Your full test.

Decisions for you

Web access?

Let Inky look things up (programming docs, formulas). It helps, but it's your call on academic integrity.

Automatic mode?

Keep and fix it (start ahead of the due date; for "try" rules too), or ship only "you ask" for now.

Ready work waits?

Let ready work wait for you until you act, instead of the 15-minute window that files it away.
