How the app works today

Studi is an Electron app. The main process owns all state and all agent work. The React renderer is a thin view that asks for state and sends commands. That split is good news: most of the redesign is renderer work.

Rendererdesktop/src/app. StudiApp, DashboardScreen, AssignmentWorkspace, DeskDrawer, ChatWorkspace, OnboardingScreen, Settings. About 4,000 lines. Polls state. Only three push events exist.
Contractdesktop/shared. Zod schemas for every record, plus the IPC contract. About 60 renderer methods, such as startAssignment, savePermissionRule, sendScanMessage.
Main processdesktop/electron. Coordinators for scan, assignment, manager queue, and conversation. A lifecycle kernel for timers and notifications. A browser controller for the school page.
StorageLocal SQLite. 24 tables, including assignments, permission_rules, manager_queue, assignment_executions, task_events, agent_messages, submission_receipts.
Agent runtimePi SDK sessions. Provider-generic, but only a ChatGPT (Codex) login is wired. Separate sessions for home chat, each assignment, and scans. A tutor target is declared but unused.
One browserA single embedded school browser with a lease. Only one assignment or one scan can drive it at a time. This is why Today has one "Inky now" row.
Preview harnessbun run preview:ui. Real components against fixtures. About 40 scenarios. This is where new screens get built and reviewed first.
Fake schoolagent-harness/lms. Six courses, 39 activities, 9 scenarios, fault injection, a private truth record for scoring.

The life of one assignment today

ScanThe scan agent reads class pages and writes assignments with evidence.school_scans, assignments
RuleresolvePermission picks the most specific rule. No rule means Inky won't start.permission_rules
QueueThe manager enqueues it and takes the browser lease. Starting is manual, or automatic as one global preference.manager_queue
WorkA worker session uses browser and file tools. Up to 24 turns and 2 attempts. It can pause for the student.assignment_executions
Review and submitA review window opens. The student submits, or Inky does under the auto rule. A receipt saves the page before and after.submission_receipts

Learn, made real

You asked when things get generated, saved, and shown. The answer is the core design decision: the model reads and teaches, and the app plans. Anything shown on the Learn page is either saved data or arithmetic on saved data, so it loads instantly and never changes by surprise.

FindThe school check notices syllabus files and exam pages. The student can also drop a file, paste text, or type a date.once per file
ReadA one-off agent job extracts exams and topics into a fixed schema. It runs again only if the file's hash changes or the student says it's wrong.model, then saved
PlanA pure function picks the exam, today's topic, the day path, and readiness.no model, every open
TeachThe tutor agent runs the session live through component tools. Blocks are saved as they happen.model, live
Recordtutor_finish writes evidence and moves a level by one step at most. The plan recomputes.saved

The planner, in shared/learn.ts

leadExam   = nearest exam with topics
gap(t)     = t.weight * (4 - level(t)) / 4
todayTopic = max gap, ties to earlier chapter
recapDue   = last session was 2+ days ago
readiness  = sum(weight * level / 4)
path       = topics by gap, a recap every third
             day, a mock exam 2 days before

All pure and unit tested like weekCalendar.ts.

A tutor session is a chat made of components

The tutor agent can only act through these tools. Each tool is one React component. The tool call does not return until the student acts, and the student's action is the result. Press "How this works" inside a session in the mock to see real calls.

ToolComponentResult sent backChecked by
tutor_sayInky's handwritten linenone
tutor_ask_choiceOption cardspicked, secondsApp, from correct
tutor_ask_typedTyped answer with a hint ladderanswer, correct, hints usedApp, from accept
tutor_show_modelOne of a small registry of hand-built modelswhat the student explored
tutor_ask_explainText box, then a written verdictthe textThe agent, against its own rubric
tutor_finishSummary and level changeupdates levels, posts a card to You and InkyApp caps the change at one step

The first version needs five components and one model (the population grid), plus flashcards. New models are added one at a time as topics demand. The app enforces the time budget, one open block at a time, and the level cap, so a bad model turn cannot corrupt what the student "knows".

Why levels only move in sessions. Inky doing HW 3 on heaps proves nothing about the student. The page says so, and the data model enforces it: only tutor_finish writes to topic_level.

The fake school has to grow

Today it models assignments, quizzes, lessons, forums, and external tools, with nine scenarios and good fault injection. It has no syllabus, exam, or calendar content at all, so none of Learn can be tested against it. It also can't trigger several of the new states on purpose.

Stories to test against

Each is a check someone can run and tick. Tier says the cheapest place it can be proven: P preview fixtures, S fake school, F full app with a live model. Ticks are saved in this browser.

Phases

Ordered so the first three ship value with almost no backend risk. Sizes are relative: S is days, M is a week or two, L is more.

Risks and open questions

RiskWhy it mattersHow to settle it
Import from Claude CodeI did not verify where Claude Code stores credentials, or whether reusing them is allowed. The mock shows the button as if it works.Spike before promising it. A pasted API key is the safe first version.
A tool call that waits for the studentTutor blocks assume a tool can stay open until the student answers. I believe the SDK's async tools allow it, but did not test it.One-day spike: a tool that resolves from an IPC call.
Planned start timesStarting homework while the student is away is a trust decision, not only a feature. Today it is one global switch.Ship "Waiting for you" first. Add planned starts only for "Do it and submit" rules, with a notification before each start.
Kind labelsRules by kind are only as good as the labels. A wrong label could auto submit an essay.Show the kind in the row's card with a way to correct it. Score it on the fake school. Treat a low-confidence label as no label.
Streaming eventsA chatty worker could flood the renderer.Batch on a short timer. Save to task_events, which already exists.
Tutor qualityThe interface is only as good as the questions. A bad question with a nice card is still bad.Start with two topics and review transcripts by hand before widening.
Still invented in the mockTime estimates, time saved, and readiness numbers.Readiness becomes real in phase 7. Drop the others unless we find an honest source.
