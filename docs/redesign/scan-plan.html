Scanning: from a 99 minute crawl to a two minute check.

An audit of the scanner on codex/studi-redesign-release, a comparison with other agent browsers, the new scan design, and one build order that covers scanning and the Learn redesign together.

Written 2026-09-20. Companion to learn-plan.html and learn-concept.html. Numbers for the real scan come from .agents/studi-qa/scan-audit-2026-09-19.md.

Audit: what happened and why

One onboarding scan of a real Moodle school: 99 minutes, 8 internal agent sessions, 655 tool calls, 112 errors or rejections, about 77M tokens (mostly re-read cached context), 5 courses, 218 “items” of which most are slides, readings and grade rows. Only 2 of 5 course inventories were complete and scan_finish was never called.

Decision: build Studi's browser the way Codex's browser use is built

Codex inspected its own installed browser plugin (C:/Users/kaust/.codex/plugins/cache/openai-bundled/browser/26.915.31945/: scripts/browser-client.mjs, scripts/browser-service.mjs, docs/api.json, docs/accessibility.md, docs/confirmations.md). That is the reference. It fits Studi directly, because it drives the page through Chromium's DevTools protocol from a trusted service, which is what Electron's webContents.debugger already gives Studi on the school browser, with the student's login intact. No debugging port, no second program. So there is no embed-versus-build question left: we rebuild Studi's browser layer to the Codex shape.

The bigger win: ask the LMS, don't crawl it

What “from the logged-in session” means: once the student has signed in to their school inside Studi's browser, that browser holds the same sign-in cookie any browser would. The Moodle dashboard doesn't have its timeline baked into the page; the page itself asks the school's server “what's due for this student?” and gets back a plain list. Studi can ask that same question from that same signed-in page and get the same list, as data: title, class, due date, link. No password is stored, no token is created, and no AI has to look at the screen and click through pages. It's what the school's own page already does, read directly.

New scan design

Four small scans with different jobs, replacing one exhaustive crawl. Deep reading moves to the moment it's needed. Every scan has one hard ceiling: 30 minutes. There are no tool-call caps. The expected times below are targets the harness reports against, not limits.

How a setup or refresh scan runs

DetectMoodle, Canvas or unknown, from page markers. No model.
Ask the LMSConnector calls the session APIs or reads the calendar. Rows saved directly. No model.
Fill gapsOnly if the connector failed or a class has no rows: the agent reads the dashboard and calendar with the batch tool.
SyllabiAgent opens each class once, follows one syllabus link, any host linked from a verified class page.
FinishThe app finishes the scan from its checklist. The agent doesn't have to remember to.

Rules the coordinator enforces

  • One ceiling: 30 minutes of active scanning per scan, any kind. Time paused for sign-in doesn't count. At 30 minutes the scan finishes as partial with what it has and says what wasn't checked. No tool-call or token caps; those are measured and reported only.
  • No-progress stop: 5 minutes without a new saved row or a newly finished class ends the scan early. This is what stops wandering long before the ceiling.
  • Same rejection three times for the same target: the target is marked skipped with the reason, shown in the scan result, and the agent is told to move on.
  • “Finish with what you found” button at any time. Saves rows, lists what wasn't checked.
  • One continuous scan: no mid-turn aborts. Context stays small because results are small, not because the conversation is thrown away. If a restart is ever needed, the carry-over is a fixed-size summary: classes done, classes left, counts. Never the rows.
  • Evidence, relaxed for lists: a row extracted by the batch tool is its own evidence (title, date text, href, captured together from one DOM row). No detail visit to prove a date.
  • What counts as work: only items with a due date or a submission type, or that the LMS itself lists on its timeline. Files, pages, slides, URLs and grade rows are not recorded by setup or refresh.
  • Inventories dropped. Completion is the checklist above, not set-equality over everything ever seen.
  • Dates: one shared parser. Missing year means the current academic year (if that date is more than six months past, roll forward a year); explicit years are kept; date-only deadlines are overdue only after the day ends. Used by Homework, scan and Learn.
  • Model: per-role model and effort. Scans run at low effort on the smaller model. Tutor and assignment work keep the current one.
  • Honest results: rejections and skips are written to scan.failures, so the UI stops understating friction.

Harness: make the benchmark able to fail

  • Noisy Moodle scenario: 5 courses, about 130 activities in one, new item kinds (file, page, url, folder, video, label), Moodle-shaped nested sections, a grades page, a small client script that re-renders sections and the drawer so refs really go stale, a “Show more” bare button.
  • University site origin: a fourth origin hosting one syllabus as HTML and one as a forced-download PDF; the harness allowlist accepts it when linked from a class page.
  • Document faults: HTML shim before the file, Content-Disposition: attachment, an image-only PDF.
  • Connector surface: /lib/ajax/service.php for the Moodle scenario and /api/v1/* for a Canvas-like scenario, with a switch to disable them so the fallback is tested.
  • Time is the gate: a run fails if it hits the 30 minute ceiling or misses its scenario's time target. A timeout is a failure, never a null. Tool calls, tokens, error rate and peak prompt size are always recorded and the run is flagged if any is more than 25% worse than the last saved run.
  • All phases every run: cold, unchanged, changed, resume.
  • Report per run: minutes, calls, tokens, errors by type, rows found vs expected, duplicates, junk rows recorded. Saved in docs/reports/ and compared with the last run.

Golden recordings of real schools

  • Record: a dev-only recorder on BrowserController's CDP session saves document, XHR and file responses (Network.getResponseBody) into agent-harness/fixtures/golden/<platform>/<case>/. That holds pages/ keyed by normalised URL, and manifest.json with status, headers, capture clock and school time zone.
  • Scrub: names, emails, student ids, sesskeys, tokens and avatars are replaced with stable fakes. The recorder refuses to save if the account holder's name or email survives the scrub. Record only with the account holder's consent.
  • Replay: a replay mode in agent-harness/lms/server.ts serves the manifest on loopback origins, as the vendor origins work today, with the recorded headers and the capture clock. Anything that wasn't recorded returns 404, so wandering shows up as misses and never reaches a live site.
  • Expected output: expected.json lists courses. For each assignment it gives platform id, title, course, dueAt or null, dueText, precision, status and kind. It also lists excluded ids, a syllabus per class, and exams with their quote. A person writes it from the pages and a second person checks it. Studi's output never becomes the expected file.
  • Two tiers: extractor tier (no model): connectors, browser_rows and the date module run on every recorded page with bun run test:golden, on every PR, deterministically. Agent tier: a full setup and refresh against the replayed site at the release model and effort, 3 runs, worst run counts, nightly and before each release.
  • Gate: CI fails if the extractor tier is below 100% on due dates, if any recall or precision target is missed, or if any date is invented. The agent tier blocks a release. Results are saved in docs/reports/ next to today's benchmark reports.

Identity, dedupe, student edits and provenance

  • Identity is platform + installation + platform id, taken from the connector or from the URL patterns above. Each pattern is added to schoolIdentity(). A known platform never uses the title for identity. Scan writes are upserts by identity, one transaction per batch (store.database.transaction), so running the same scan twice records zero changes.
  • Renamed: same id, new title. One title change, and the old title is kept as an alias for search. Moved: same id, new course. One course change. Gone: missing from two complete reads of its class in a row. It's marked removed and hidden from Today, never deleted, because tasks and artifacts may point at it.
  • LMS row plus linked-system row: merged into one assignment with two sources only when the LMS row's link launches that linked assignment, or when course, normalised title and due instant all agree. Anything else stays as two rows and goes into assignmentConflicts (assignment-reconciliation.ts) for the student. Never merge on title alone.
  • Student edits win and are surfaced. Title, course, due date, kind and “not homework” each hold a school value and a student value, the way dueDateOverride already does. Scans write only the school value. If the school value changes under a student value, the change is recorded with conflict: true and shown once: “School moved this to Oct 9. You had Oct 12. Keep yours · Use school's.” Learn exam dates follow the same rule (dateOrigin: "student").
  • Provenance per field: provenance.{title, course, dueAt, status, instructions, kind} = {evidenceId, via, quote, capturedAt}, where via is api, row, detail, document, inferred or student. quote is the exact source text (dueText already is one). This replaces the ever-growing evidence[] with the last capture per field (audit #7).
  • Confidence comes from via, not from the model: api, row, detail and document are exact; inferred means check (kind from classifyAssignmentKind, a resolved relative date); student means yours. assignmentWorkEligibility refuses an inferred due date.
  • In the UI: each field on the assignment page shows “Found on <page title> · Sep 21” and links to the source. “This is wrong” saves the field, its provenance and that slice of the trace into the scan report.

Dates and time zones

  • One module, desktop/shared/due-date.ts, takes in zoned-deadline.ts, requireObservedDueAt and assignmentDue. Scan, Today and Learn all import it. This is the “shared date parser” of step 1.
  • The school's time zone comes from the site (Canvas ENV.TIMEZONE, the Moodle profile or calendar export) and is stored on SchoolProfile. API instants with an offset are used as they are.
  • A date with no time has precision date and is due at the end of that day in the school's zone. For a missing year, use the rule in the design section.
  • Relative dates (“Friday”, “tomorrow”, “end of week”, “next class”) keep their dueText with precision unknown. They are resolved only when the same page gives an absolute anchor (“Week of Sep 21”). A resolved date has via: inferred, quotes its anchor, shows as “Fri Sep 25?” until confirmed, and is never eligible for automatic work.
  • “11:59 PM Friday” is 23:59 that Friday. “Midnight Friday” alone is ambiguous, so it becomes the end of Friday with precision date. Daylight-saving gaps and repeats stay unresolved, as zoned-deadline.ts already does.
  • Never use the computer's time zone, never let Date.parse fill in a year, and never turn a non-due label (“Opened: Oct 1”, “Posted”, “Available from”) into a due date. Only text labelled due, deadline or closes becomes dueAt.

Trace, scan report, canaries

  • Trace: one scan-trace.jsonl per scan in app data. It records events for pages, tools, model calls, saved rows, blocked writes and failures, each with URL, milliseconds, tokens (the TelemetryAgentFactsSchema fields) and the row ids saved from each page. It rotates at 5 MB.
  • Scan report: opened from the scan result. It shows time, pages, calls and tokens, what was found on which page for each class, what couldn't be checked, blocked writes and failures. A plain page, scrubbed and included in the diagnostics export (diagnostics.ts). Telemetry sends the target numbers only, never titles or URLs.
  • Canaries: every release build runs S1, S4, S5, S12, S17 and the golden extractor tier; any failure blocks publishing. A nightly agent-tier run catches changes on the model provider's side.
