Bug 1 — Opening the live card hides the real school page

What a student sees. Inky is working. The desk sidebar shows the live school page. They click that same week card to read the details. The page disappears. A dashed empty box stays in the drawer. The week column and the drawer no longer agree on width.

Why. Three flags mean “is the desk open?” and they disagree.

  • StudiApp.tsx only shows the guest view when panel.kind === "desk".
  • Clicking a card sets panel to { kind: "assignment" }.
  • DeskDrawer still treats that live assignment as a desk (desk = panel.kind === "desk" || live) and keeps .drawer-school-slot.
  • Week width only shrinks for is-desk-open, which is also panel.kind === "desk".
const showSchoolPage = deskOpen && panel.kind === "desk" && activeExecution;
// openAssignment() → setPanel({ kind: "assignment", assignmentId })
// Electron then setBrowserLayout({ mode: "hidden" })

Fix 1 — One meaning of “desk is open”

  1. Derive one value, e.g. showingLiveDesk: sidebar is open and a run is live and that run is the assignment on screen (or the panel is plain desk).
  2. Drive all four from that value: setBrowserLayout, .is-desk-open, .workspace-drawer.is-desk, and the school slot.
  3. If they click the live card, keep the page up. Do not flip to a peek that hides Electron.
  4. Closing the sidebar may hide the page (that matches the written rule). Opening the live card must not.
const live = isLivePhase(lifecycle.execution);
const viewingLive =
  live &&
  (panel.kind === "desk" ||
    (panel.kind === "assignment" && panel.assignmentId === lifecycle.execution.assignmentId));
const showSchoolPage = screen === "week" && viewingLive;

Verify 1

  1. In Electron, start a real or fixture assignment so a run is working.
  2. Open Inky’s desk. The guest page must sit in the sidebar slot, not over the week board.
  3. Click that same week card. The page must stay. No empty dashed box. No overlap.
  4. Click a different card. The live page may hide; the other card is a peek. Inky keeps working in the background.
  5. Click Inky’s desk again. The page comes back on the live run.

Bug 2 — “Make Inky do this” can shove the queue, then open the wrong desk

What a student sees. Homework B is already running. They peek at homework A and press Make Inky do this. An error appears. They are thrown onto B’s desk. A is now queued and priority-bumped even though start failed.

Why. The handler mutates first, then starts. The button does not know a global run is live. The UI always opens the desk, even when action() swallowed the throw.

// electron/main.ts
manager.enqueue({ taskId });
manager.steerNext(taskId);
await assignmentExecutionCoordinator.start(taskId); // throws if something is already live

// StudiApp.tsx
await updateLifecycle("assignment", () => studi.startAssignment({ taskId }));
setPanel({ kind: "desk" }); // runs even when start failed

// DeskScreen.tsx
const canStart = task.state is discovered|queued && mayAttempt && !live;
// `live` is only true for THIS card’s assignment, not “any run”

Fix 2 — Do not enqueue unless start can happen

  1. If any execution is working | needs_user | ready_review | submitting, startAssignment must return/throw before enqueue / steerNext.
  2. Or: start first; only enqueue/steer after the coordinator accepts the task.
  3. Disable Make Inky do this whenever any run is live, not only this card.
  4. In startThisAssignment, open the desk only if the returned state has that taskId as the live execution.
startAssignment: async ({ taskId }) => {
  await requireReadyProviderForScan();
  const live = requireLocalStore().lifecycle.getActiveExecution();
  if (live && isBusyPhase(live.phase)) {
    throw new Error("Inky is already on another page.");
  }
  const manager = requireManagerCoordinator();
  manager.enqueue({ taskId });
  manager.steerNext(taskId);
  await requireAssignmentExecutionCoordinator().start(taskId);
  return requireAppKernel().state();
};

Verify 2

  1. Programmatic: start task B, then startAssignment(A). A must stay discovered (or whatever it was). Queue order/priority must not change. Receipt or store dump is enough.
  2. In the UI, with B live, open A. The yellow start button must be off, or it must no-op without opening B’s desk as if A started.
  3. With nothing live, start A from a discovered card. It must enqueue, become the live run, and open the desk on A.

Bug 3 — Sidebar talk and “Inky already worked on this” are not scoped to the open card

What a student sees. They talk about A. They open B. A’s chat is still in the drawer. Or they peek at A while B is running and see B’s checkpoints under A’s title.

Why. The 900ms poll always loads lifecycle.execution.taskId into detail. Talk lines render whenever talk.key is non-empty, and openAssignment does not reset the key.

// poll
if (lifecycleState.execution?.taskId) setDetail(await getTaskDetail(that live id));

// drawer
talk={talk.key ? talk.lines : []}
detail.attempts.length > 0 && !live  // no assignmentId check

Fix 3 — Key detail and talk by assignment

  1. Only keep detail if detail.assignment.assignmentId matches the open card (or the live desk).
  2. On openAssignment, set talk to that assignment’s key (empty lines if new). Do not show another key’s lines.
  3. Stop the poll from overwriting a peek with the live task.
  4. Week-board Inky reply staying off the board when the drawer is open is already correct. Keep that.
const openId = panel.kind === "assignment" ? panel.assignmentId : live?.assignmentId;
const visibleDetail = detail?.assignment.assignmentId === openId ? detail : null;
const visibleTalk = talk.key === (openId ?? "desk") ? talk.lines : [];

Verify 3

  1. Open A. Type “what is this?” Send. Open B. B’s talk field is empty. A’s lines are gone.
  2. Start B. Open A as a peek. “Inky already worked on this” must not show B’s tools under A’s title.
  3. Reopen A. The earlier A chat is back (same key) or honestly empty if you chose not to persist — pick one and stick to it.

Bug 4 — The real school page is a guessed rectangle

What a student sees. The guest page covers the title, actions, or sits in the wrong place. On a short window the CSS stacks the drawer under the board (max-width: 1000px), but Electron still parks the page on the right.

Why. schoolBrowserBounds hard-codes y: 192 and “54% across.” The slot lives inside .drawer-scroll, after meta, buttons, and banners. Overlay click-targeting follows those wrong bounds.

const start = Math.round(width * 0.54);
return { x: start + 14, y: 192, width: ..., height: height - 276 };

Fix 4 — Place the guest view on a fixed slot, not inside the scroll

  1. Make the school pane a non-scrolling region of the drawer (below the head, beside or under a short meta row). Scroll only the notes / talk / history.
  2. Measure that slot from the renderer (getBoundingClientRect) and send it to main, or keep math in main but derive it from the same CSS that sizes the slot (same left, top, width, height, including the 1000px stacked layout).
  3. Until the slot exists, mode: "hidden". Do not paint a 192px guess.

Verify 4

  1. Desktop width (~1280). Start a run. The live page must sit inside the dashed/paper slot. Title and I’ll take over stay above it and clickable.
  2. Resize to ~900px. CSS stacks the drawer. The guest view must follow the stacked slot, not stay on the right over the week cards.
  3. Scroll the talk / history. The school page must not scroll away or smear.
