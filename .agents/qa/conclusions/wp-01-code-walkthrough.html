The mental model

WP-01 has two jobs. It defines valid data, and it defines where untrusted data gets checked. Everything else in the app will build on those decisions.

Pure domain code

Assignments, permissions, tasks, runs, events, and tool envelopes live in shared/. These modules do not open windows, call the network, or write files. Give them values and they return a result.

Electron boundary code

The renderer can call named methods. The preload forwards the request. Main validates it, runs the handler, validates the response, and sends the result back.

The rule worth remembering. TypeScript helps while writing code. Zod checks values while the app is running. Studi uses both because browser data and stored data can be wrong even when the source code compiled.

Journey one: the renderer asks for runtime information

The production method takes no argument and returns the Electron, Chrome, Node, and Studi versions. A transforming test method proves the same design also works when input and output types change during validation.

The registry defines the whole method

studiIpcRegistry binds a public method name to one fixed channel, one request schema, and one result schema. That single record generates both ends of IPC.

getRuntimeInfo: { channel: "studi:runtime-info", requestSchema: z.undefined(), resultSchema: RuntimeInfoSchema }
shared/ipc.ts

TypeScript derives the caller signature

IpcApi maps over every registry entry. Request-bearing methods accept the schema's input type. Their promises resolve to the result schema's output type.

type IpcMethod<Definition> = ( ...args: RequestArguments<Definition> ) => Promise<z.output<Definition["resultSchema"]>>;
Caller suppliesz.input<request>
Handler receivesz.output<request>
Caller receivesz.output<result>

The renderer sees one typed object

window.d.ts says that window.studi is the API generated from the registry. The React app does not copy the runtime-info shape. It imports the shared type and calls getRuntimeInfo().

interface Window { readonly studi?: StudiApi; } window.studi.getRuntimeInfo()
src/types/window.d.ts · src/app/StudiApp.tsx

The preload exposes named methods only

createIpcApi builds and freezes the object. It checks how many arguments the caller supplied. Then it invokes the channel stored in the registry. The renderer cannot provide its own channel name.

const studiApi = createIpcApi( studiIpcRegistry, (channel, request) => ipcRenderer.invoke(channel, request) ); contextBridge.exposeInMainWorld("studi", studiApi);
electron/preload.cts

Main checks the request once

createIpcHandlerRegistrations builds the main-side registrations from the same registry. Its wrapper parses raw renderer input before calling the handler.

const request = contract.requestSchema.parse(rawRequest); const result = await handler(request);

A bad request still crosses Electron, because main is the trust boundary. It stops before the typed handler does any work.

The handler returns schema input

The handler receives normalized request output. It returns the result schema's input. This distinction matters for transforms. A handler may return "accepted", while the schema turns that string into the number 8.

Journey two: an assignment becomes allowed work

WP-01 does not scan a school or execute an assignment. It defines the decisions those later systems must make before work or submission can happen.

A scanner produces an assignment candidate

AssignmentSchema requires a course, title, safe source URL, discovery time, and evidence. Strict objects reject unknown fields. Version 1 is explicit.

{ schemaVersion: 1, assignmentId: "assignment-42", courseId: "csc-316", title: "Worksheet 7", sourceTarget: "https://school.example/worksheet/7", discoveredAt: "2026-08-31T14:00:00.000Z", evidence: [] }
shared/assignment.ts

The source URL is screened for credentials

SafeSourceTargetSchema allows HTTP and HTTPS, rejects embedded usernames and passwords, and blocks secret-shaped query or fragment keys such as token, cookie, and client_secret.

This is schema-level protection, not the whole privacy system. Later capture and export code must still redact summaries and opaque references before they leave the computer.

shared/ids.ts · shared/evidence.ts

The permission resolver finds the most specific rule

resolvePermission filters matching rules, then sorts by assignment, pattern, course, and global scope. Newer rules win equal scopes. A stable rule ID breaks the final tie.

assignment > pattern > course > global no match => do_not_attempt attempt => mayAttempt: true, maySubmit: false auto_submit => mayAttempt: true, maySubmit: true

Pattern rules must match both a pattern ID and the course. A similar title in another class cannot grant submission permission.

shared/permission.ts

A task changes state through one function

transitionTask looks up the allowed destinations for the current state. An invalid move returns a typed rejection and leaves the task untouched.

discovered -> queued queued -> working working -> needs_user | ready_review | submitting submitting -> submitted | needs_user | working | failed

A valid move creates a new task revision and a matching task_state_changed event. The function does not write storage or read the clock.

shared/task.ts

The event proves what changed

The event records the task and run IDs, sequence, time, prior state, next state, and new revision. verifyEventOrder rejects duplicate or decreasing sequence numbers.

{ aggregateType: "task", runId: "run-9", sequence: 12, type: "task_state_changed", payload: { from: "working", to: "ready_review", revision: 4 } }
shared/event.ts · shared/task.ts

A future browser mutation carries enough identity

ToolMutationEnvelopeSchema requires task, run, tab, tool-call, and idempotency IDs plus the page revision the agent expects. The result repeats those IDs, records the new page revision, and attaches evidence.

This does not control a browser yet. It gives WP-04 and WP-05 a contract that can reject stale or duplicated mutations.

Journey three: how the tests prove the design

The useful tests follow the same boundaries as production. They do not call a fake helper that skips main validation.

Debug it without wandering through the repository

Start at the value that failed

If parsing failed, identify the schema and inspect its Zod error path. Do not begin in React or Electron.

Check the pure decision

For task or permission failures, reproduce the input with the focused contract test. These functions have no runtime dependencies.

Check the shared IPC composition

For bridge failures, run node --test tests/contracts/ipc.test.mjs. Confirm the registry, arity, request parse, handler, and result parse in that order.

Cross the actual desktop boundary last

Run npm run test:electron. Inspect preload exposure, main registration, renderer readiness, malformed-result rejection, and temporary-profile cleanup.

What to carry into WP-02

The database should store only values accepted by these schemas. Rebuilding a task projection should replay ordered events through the same transition rules. Permission records should preserve course-bound pattern identity. Storage must not invent a second version of any WP-01 type.
