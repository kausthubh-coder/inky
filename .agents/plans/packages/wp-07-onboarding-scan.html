WP-07 · approved implementation dossier

First-run setup ends with a real, evidence-backed school scan.

Studi asks for the minimum local preferences, opens the persistent school browser for sign-in, then lets a real Pi scan discover courses, assignments, and linked systems through the general browser tools. Nothing appears as verified unless the scan recorded current browser evidence.

Observable outcome

Name and defaults→Codex ready→school URL→visible sign-in→real scan→verified courses and assignments→replayable workflow

The same screen must show honest progress, pause when the student must sign in, preserve partial results, and allow a later replay to rediscover the school rather than trusting old rows.

One state owner

Electron owns one SchoolScanCoordinator. SQLite owns the school profile, scan run, verified courses, linked systems, coverage, and failures. Existing assignment storage owns normalized assignments. The artifact store owns one versioned scan-workflow Markdown file. React only projects state and sends typed commands.

Core data shape

  • SchoolProfile: student name, root URL, default permission, preferred scan cadence, onboarding state.
  • SchoolScan: ID, state, started/completed time, current step, coverage, failures, and handoff.
  • Course and LinkedSystem: stable local ID, label, safe source target, last verified scan, evidence.
  • ScanWorkflow: root target plus concise navigation hints and coverage goals. Never cookies, HTML, passwords, or auth headers.

Implementation sequence

  1. Add the smallest shared schemas and versioned SQLite migration for the profile, scan, courses, linked systems, and evidence-backed coverage.
  2. Add direct repositories and one scan coordinator. Reuse the existing assignment repository, evidence schema, artifact store, browser controller, Pi runtime, and manager queue.
  3. Fix the WP-06 follow-up so re-enqueuing an existing task without a supplied priority preserves manual steering.
  4. Create a scan Pi session with the general browser tools plus narrow record-course, record-assignment, record-linked-system, handoff, and finish tools. Each recording tool binds its claim to the coordinator's latest current-page snapshot and scan ID.
  5. Run the agent against the visible browser. A sign-in page produces needs_user. The student signs in inside the page, then explicitly resumes. No password field enters Studi.
  6. Commit discovered rows incrementally. Completion requires explicit coverage and at least one verified course. Zero results remain incomplete. A partial or failed run never deletes prior verified rows.
  7. Write or revise one workflow artifact only after a successful scan. Replay supplies the workflow as hints, opens the root again, and re-observes every claimed item.
  8. Build the smallest first-run UI in the approved Studi style. Show profile choices, runtime status, browser handoff, live scan step, verified counts, failures, linked-system sign-ins, missed-course feedback, and the resulting school view.
  9. Expose typed IPC only for onboarding state, profile save, start/resume scan, replay, and missed-course feedback. The renderer cannot write courses, assignments, evidence, or completion.
  10. Perform a subtraction pass, then run the focused and inherited gates.

Named risks worth proving

  • An unauthenticated or expired session pauses for the user and does not mark login verified.
  • A zero-result scan stays incomplete and cannot seed a dashboard.
  • A partial scan keeps prior verified courses and assignments.
  • A linked system remains needs_user until a browser observation verifies its signed-in state.
  • Replay starts at the school root and re-discovers items instead of projecting the old workflow as current data.
  • Recorded source targets reject secret-shaped URLs and no page HTML enters SQLite or Markdown.

Explicit exclusions

  • No LMS-specific Moodle scanner or per-site adapter.
  • No automatic scheduler execution, tray lifecycle, or native notification. WP-08 owns them.
  • No assignment worker start, answer generation, takeover timer, submit, or fallback answer. WP-09 owns them.
  • No pattern clustering framework. The scan may record an observed repeating label, but only a later explicit student confirmation can create a permission match.
  • No fake LMS as the final proof and no seeded production assignments.

Pass conditions

  • A fresh profile can complete onboarding through the real Electron UI without a password field.
  • A real signed-in Codex-backed Pi scan uses Studi tools against the user's visible Moodle and persists at least one verified course plus the assignments the current coverage can reach.
  • Every displayed row points to the scan and safe browser evidence that created or refreshed it.
  • The tester uses official Playwright MCP through Electron's loopback CDP endpoint for the Studi renderer, while the embedded Moodle remains the visible source of truth.
  • Sign-in handoff, partial preservation, zero-result incompleteness, linked-system handoff, workflow write, and replay re-observation pass at the closest useful boundary.
  • Typecheck, storage, agent, Electron, contracts, foundation, build, and protected Sites gates remain green where touched.
  • The final reviewer finds no concrete blocker in elegance, traceability, or maintainability.

Fail conditions

WP-07 fails if the renderer or model can declare completion directly, old rows masquerade as a successful replay, a failed scan creates sample schoolwork, credentials or page HTML enter app storage, linked systems appear connected without browser evidence, or an LMS-specific execution path replaces the general browser tools.
