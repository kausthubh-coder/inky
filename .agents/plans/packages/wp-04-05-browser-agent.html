WP-04 + WP-05 · verified 2026-09-01

A real Codex-backed Pi agent controls Studi's visible school browser.

This combines the embedded-browser controller and Pi browser tools because the useful proof crosses both. The final live check uses an actual Moodle account after the user supplies the URL and signs in.

Outcome

Studi opens one visible persistent WebContentsView. A real Pi session authenticated through the built-in openai-codex provider observes and safely operates that same browser through Studi-owned tools.

User path

Open Studi, connect the Codex subscription, enter the school URL, sign in inside the embedded browser, then ask the agent to inspect or navigate a real Moodle page while every action stays visible.

Smallest useful shape

  • Electron main owns one browser profile, one visible view, and one CDP attachment.
  • The controller exposes a small set of page operations. Pi never receives raw CDP access.
  • A snapshot has a page revision and bounded element refs. An action rejects refs from an older revision.
  • Pi tools map directly to controller operations. Ordinary click cannot approve a known submission control; submission remains a separate explicit tool.
  • The existing Pi runtime gains real openai-codex login and model selection. Credentials stay in Pi's app-owned credential store.

Implement now

  1. Create and lay out the persistent visible browser.
  2. Attach Electron's debugger transport and recover from detach when safe.
  3. Navigate, snapshot, click, type, select, press keys, and wait using CDP.
  4. Return concise post-action evidence.
  5. Register these operations as the only Pi tools.
  6. Add the real Codex subscription login path.
  7. Add only focused programmatic checks the implementer needs.

Do not build

  • No hidden Playwright or second browser.
  • No fake LMS application.
  • No LMS-specific completion code.
  • No manager queue, scheduling, memory, downloads framework, or polished onboarding.
  • No broad browser automation framework or raw CDP passthrough.
  • No automatic submission during the live Moodle proof.

Live tester path

  1. Launch the real desktop app.
  2. Use Studi's Pi login path to authenticate the user's ChatGPT Plus/Pro Codex subscription.
  3. Ask the user for the Moodle URL and let the user sign in inside the visible embedded browser.
  4. Run a real Pi agent request that snapshots the page and uses Studi browser tools to reach a user-selected safe course or assignment page.
  5. Confirm the browser stayed visible, the same profile retained login, the agent received bounded observations, and no submission occurred.
  6. Restart Studi and confirm the browser login and Pi provider remain usable.

The tester changes no code and adds no automated tests. If the run fails, it records the shortest reproduction and stops.

Verified result

A real Codex-authenticated Pi session operated the visible embedded browser on the user's Moodle through Studi tools and could not submit through an ordinary click. Direct relaunch now restores the correct Studi renderer and Codex readiness. A full process quit may require LMS reauthentication because Studi does not extend identity-provider session cookies; WP-08 will preserve the normal window-close session through the tray lifecycle.

Reviewer standard

Rate the implementation out of 10 for elegance, traceability, and current maintainability. Approve a good implementation. Block only failed approved behavior or a clearly simpler design with meaningful current benefit. On live-test failure, diagnose and write the repair brief.

Debug order and sources

Start at view creation and persistent session, then bounds and navigation, debugger attachment, snapshot/ref generation, controller actions, Pi tool mapping, Codex login, and finally the live agent turn.
