Procedure

Implementation order

  1. Record tool versions, current file list, protected hashes, and baseline Sites results.
  2. Remove the old app-specific files under src/ and electron/ with explicit file edits. Do not use a broad recursive delete.
  3. Add strict TypeScript configuration and the fresh entrypoints shown above.
  4. Create a minimal BrowserWindow with nodeIntegration:false, contextIsolation:true, and sandbox:true.
  5. Expose a frozen, read-only preload method that returns app, Electron, Chrome, and Node versions.
  6. Render one honest foundation screen with an app-ready test marker. Do not recreate the old dashboard.
  7. Add the clean-room import check, protected-file hash check, build-shape check, and Electron self-test.
  8. Wire npm test, npm run build, npm run test:sites, and npm run test:electron.
  9. Run every gate and write the implementer report. Do not claim independent verification.

Pass and fail

Pass when

  • Fresh source and Electron entrypoints launch and build.
  • Strict type checks and every automated gate exit 0.
  • The four protected files retain their recorded SHA256 values.
  • The new app imports no discarded prototype module.
  • The Electron smoke test uses isolated temporary state and leaves the normal browser profile untouched.
  • The evidence ledger contains implementer, tester, and reviewer reports for the same cycle.

Fail when

  • Any current App, Onboarding, Moodle, school-workflow, direct Codex, seeded-data, or scripted-stage code remains in an active runtime path.
  • A protected file changes.
  • A test requires a real school account, stored browser profile, or model call.
  • The renderer gains Node access or the preload exposes arbitrary IPC.
  • The tester changes production code or the reviewer changes any file.
  • A role marks the package complete without manager closeout.
Failure handling

Debug order and containment

  1. Confirm Node, npm, Electron, Vite, and TypeScript versions.
  2. Check compiler output and the Electron main entry path.
  3. Check preload resolution, renderer URL, and app-ready marker.
  4. Check temporary userData and process cleanup.
  5. Check protected hashes and Sites output shape.
  6. If a native or package limitation changes the foundation architecture, stop the cycle and return the decision to the manager.

Containment is simple. WP-00 has no user data or migrations. A failed cycle leaves its reports in .agents/qa/evidence/wp-00. The next implementer receives the exact failure and starts a new cycle.
