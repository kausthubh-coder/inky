WP-13 · ready dossier

A Windows build a friend can install and recover.

This package turns the proven desktop runtime into one private-beta installer. It does not redesign Studi or invent an updater service: it bundles what already works, keeps mutable state in Windows user data, and gives testers a safe diagnostic export.

Observable journey

download installer→install→launch from Start→sign in→use Studi→install newer build→state survives→export safe diagnostics

One packaging owner

  • Electron Forge owns packaging and the Windows installer; no second packager or custom installer framework.
  • The existing Vite renderer and Electron TypeScript build remain the application build.
  • Package metadata names bundled runtime assets explicitly. A packaged app must not depend on global Node, npm, Codex, or the source tree.
  • Mutable SQLite, Markdown artifacts, browser partitions, auth vault, preferences, telemetry settings, and logs remain under app.getPath('userData').

Small release shape

  • Use one Windows installer target and one unpacked build for fast diagnosis.
  • Bundle Pi packages, native dependencies, migrations already compiled into the app, renderer fonts/replay bundle, tray/app icons, and third-party notices.
  • Expose app version and a single diagnostics-export command in Settings.
  • The export contains a manifest, runtime versions, storage health/schema, redacted recent diagnostics, and no credentials, school URLs/content, page HTML, prompts, cookies, tokens, OAuth state, or answer artifacts.

Implementation sequence

  1. Capture the current build, Electron, storage, auth, agent, telemetry, and Sites gates. Hash the four protected Sites source files before packaging work.
  2. Add Forge with the smallest Windows maker that produces an installable artifact in this environment. Configure packaged entrypoints, ASAR/resources, metadata, icon, and license notices. Do not duplicate the Vite build graph.
  3. Make packaged path resolution explicit only where development assumptions fail. Delete development-only fallbacks from packaged execution instead of adding broad compatibility layers.
  4. Add a typed diagnostics snapshot owned by the main process and a renderer action in Settings. Generate it into a user-selected or temp export path with an allowlist; never recursively zip userData.
  5. Before a schema migration, create one validated local backup tied to app/schema version. Reuse the existing backup and recovery code; do not add a second persistence system.
  6. Build the installer, install it, launch from the Start-menu registration, and run the normal approved-user path with no global Codex dependency.
  7. Seed only safe local test state through the app, close it, install a newer version over the first, then verify auth entitlement cache, browser partition, preferences, SQLite state, and Markdown artifacts remain readable.
  8. Exercise offline launch after prior approval, diagnostics export/redaction, explicit quit, uninstall, and reinstall. Verify user data is preserved unless the uninstaller explicitly offers removal.
  9. Run the Sites build/gate and compare protected-source hashes. Finish with one subtraction pass and one read-only quality review.

Current costly risks

  • Dynamic/native Pi or SQLite files are missing from the package.
  • Production resolves assets relative to the source checkout.
  • An upgrade starts with a new browser partition or user-data directory.
  • Diagnostics accidentally copy school/auth material.
  • Installer scripts mutate a protected Sites handoff source.

Deliberately not building

  • No auto-update server, delta updates, signing/notarization pipeline, macOS/Linux packages, crash-upload service, or installer analytics.
  • No generic release framework, package-provider adapter, recursive log collector, or compatibility layer for arbitrary historic schemas.
  • No claim that an unsigned beta avoids SmartScreen; the tester note explains the expected warning.

Pass

  • A Windows installer is produced and a clean installed app launches without Node/npm/Codex or the source checkout.
  • One real approved-user/runtime path works in the installed build.
  • An update-over-install preserves the persistent browser session and local Studi state.
  • Offline-after-login, old supported database migration/backup, tray lifecycle, and safe diagnostics export have retained evidence.
  • Diagnostic canaries and school/auth secrets are absent, all existing high-value gates remain green, and the protected Sites source hashes are unchanged.

Fail

The package fails if installation requires a developer toolchain, the app reads from the repository, a newer build loses user data/browser state, diagnostics include sensitive content, or protected Sites source changes. A SmartScreen warning on the unsigned private beta is documented—not hidden or treated as a product failure.
