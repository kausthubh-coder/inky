WP-10 · approved continuous-build dossier

Only invited students enter; their school life still stays local.

This package adds real desktop sign-in and beta entitlement without turning Clerk or Convex into a second school database. Electron main owns OAuth, tokens, and cloud calls. React receives one small, non-sensitive auth projection.

Observable outcome

Sign in→system browser→PKCE loopback callback→Convex checks beta access→approved: onboarding·denied: waitlist screen

An approved tester can restart offline for a bounded period using the last signed entitlement. Sign out removes the local credential and returns to the gate.

Small ownership model

  • AuthCoordinator in Electron main owns the OAuth transaction, in-memory access token, encrypted refresh token, refresh, sign-out, and renderer-safe state.
  • CloudAccountClient is the single main-process Convex boundary. It receives only typed account DTOs.
  • Convex owns beta access, entitlement/credits, aggregate usage, feedback, and one active device registration.
  • React can request sign-in/out and render state; it never receives an OAuth token.

Security shape

  • Public Clerk OAuth client; Authorization Code with S256 PKCE, random state and nonce.
  • A temporary loopback server binds 127.0.0.1 on an ephemeral port and closes after one valid callback or timeout.
  • Refresh token is encrypted with Electron safeStorage. If secure storage is unavailable, it remains memory-only and the user signs in again after restart.
  • Access and ID tokens remain in main-process memory. No Clerk secret is packaged.
  • A cached offline approval is signed/bound to the same Clerk subject, device, and a 24-hour maximum age; it cannot turn a prior denial into approval.

Implementation sequence

  1. Link this repository to the existing Clerk studi development app and create or update one explicit public desktop OAuth client. Record IDs and non-secret metadata only; keep generated environment files ignored.
  2. Add one versioned auth/device slice to local storage for the encrypted refresh token reference, stable device ID, and bounded entitlement cache. Do not add cloud-backed school models.
  3. Implement the main-process PKCE loopback flow using Clerk authorization metadata. Verify state and nonce, accept the callback once, exchange the code in main, fetch the user identity, and close the listener.
  4. Implement refresh, revoked-token handling, offline startup, and sign-out. Sign-out clears tokens, cached entitlement, Convex auth, and exposes one identity-reset hook for WP-11.
  5. Create the narrow Convex project with authenticated functions and validators for users, beta access, entitlement, aggregate usage, feedback, and active-device registration. Read paths use indexes; privileged approval mutation is internal/admin-only.
  6. Configure Convex OIDC for the Clerk issuer and desktop OAuth audience. The main process supplies refreshed JWTs to the Convex client.
  7. Expose an allowlisted IPC contract: auth state, sign-in, sign-out, retry entitlement, and submit feedback. Gate onboarding and the manager runtime before they initialize for denied users.
  8. Add compact sign-in, checking, approved-offline, denied/waitlist, and recoverable-error views in the existing Studi language.
  9. Run focused protocol/storage checks, deploy Convex once, then test the production Electron app through a real system-browser sign-in with one approved account. Exercise denial using cloud truth rather than a renderer toggle.

High-value cases

  • Wrong state or nonce: reject and retain signed-out state.
  • Duplicate callback: first valid callback wins; later requests cannot exchange again.
  • Revoked refresh token: erase it and require sign-in.
  • Offline restart after approval: bounded offline entry for the same user/device only.
  • Unapproved account: blocked before school onboarding or browser automation starts.
  • Sign out: no token, cached approval, cloud identity, or future analytics identity survives.

Explicit exclusions

  • No school courses, assignments, URLs, browser state, agent sessions, rules, queues, memories, or transcripts in Clerk or Convex.
  • No billing checkout, waitlist marketing site, multi-device synchronization, organizations, custom auth web UI, or admin console.
  • No home-grown JWT library, generic cloud repository layer, or speculative provider abstraction.
  • WP-11 owns PostHog. WP-10 only provides the identity-reset seam.

Real test

Launch the production Electron build, click sign in, complete Clerk in the system browser, return through the ephemeral loopback callback, and confirm the approved account reaches onboarding without any token appearing in renderer state or DevTools. Restart online, restart offline, sign out, and verify denial with an unapproved identity or a controlled beta-access revocation. Inspect Convex for only the permitted account/device rows.

Pass conditions

  • Approved user reaches onboarding through real Clerk + Convex; unapproved user cannot initialize school workflows.
  • State, nonce, S256 PKCE, one-shot callback, refresh revocation, offline cache, and sign-out boundaries behave truthfully.
  • Renderer and packaged output contain no refresh/access token or Clerk secret.
  • Convex rejects unauthenticated account reads and public entitlement mutation; only the approved narrow schema exists.
  • Existing contracts, storage, agent, Electron, build, and protected Sites gates remain green.
  • One read-only reviewer rates the green diff at least 8/10 for directness, maintainability, and lack of unnecessary code.

Fail conditions

The package fails if renderer code can read credentials, a callback can be replayed, an expired/revoked identity keeps online access, cached denial becomes approval, school data crosses the cloud boundary, an unauthenticated client can approve itself, or the implementation adds layers that do not serve a current behavior or named risk.
