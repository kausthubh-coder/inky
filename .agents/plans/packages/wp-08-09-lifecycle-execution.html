WP-08 + WP-09 · approved combined implementation dossier

Studi keeps working, completes safe schoolwork, and never loses the answer.

This cycle connects Electron lifecycle to the existing durable queue and visible-browser worker. Closing the window hides Studi. A persisted schedule wakes once. A supported assignment reaches user review, verified submission, honest handoff, or a Markdown fallback—then the queue can continue.

Observable outcome

Queue assignment→hide window→one worker uses visible browser→review or allowed submit→receipt or Markdown fallback→next task

Restarting during work restores the truthful paused state and pending deadline. It must not repeat a scheduled wake, submit twice, or discard page answers.

Small ownership model

  • AppKernel owns the single-instance lock, main-window visibility, tray, schedule wake, notifications, and startup reconciliation.
  • AssignmentExecutionCoordinator owns one leased task from worker start through handoff, review, submission, preservation, or failure.
  • SQLite owns schedule intent, wake claim, execution checkpoint, retry attempts, review deadline, notification intent, and submission receipt.
  • The existing task event stream remains the canonical task state; existing permission resolver remains the only submission authority.
  • The artifact service remains the only Markdown writer. React only invokes typed commands and projects state.

One durable execution shape

  • AutomationSchedule: enabled/paused, cadence, next run, last claimed occurrence.
  • AssignmentExecution: task, phase, task budget, attempt count, return predicate, review deadline, answer snapshot, last error.
  • ExecutionAttempt: ordinal, concise plan, result, browser evidence.
  • NotificationIntent: kind, task/scan target, delivered/clicked time.
  • SubmissionReceipt: pre-submit evidence, post-submit evidence, verified status text/time. A click alone is never a receipt.

Implementation sequence

  1. Add only the shared schemas and one versioned migration required by lifecycle schedules, execution checkpoints, review deadlines, notification intents, and submission receipts.
  2. Create an Electron app kernel around the current composition root. Acquire the single-instance lock before initialization. Closing the main window hides it; explicit tray Quit is the only normal quit. Tray Open focuses Studi, Pause toggles scheduled automation, and status summarizes current work.
  3. Persist normalized daily/weekly/manual next-run intent. Reconcile at startup and resume: claim at most one due occurrence, coalesce missed occurrences, calculate the next future time, then call the school scan coordinator. Use an injected clock/timer seam rather than a generic job framework.
  4. Persist notification intent before presenting a native notification. Handoff, review-ready, scan result, and failure notifications carry the exact task or scan target. Clicking focuses the main window and matching browser/task state.
  5. Extend the manager with one assignment execution coordinator. It receives the stored assignment, fresh browser snapshot, resolved permission, relevant preferences/rules, and a bounded task budget. It resumes the existing worker session rather than creating a second browser owner.
  6. Expose narrow worker tools for recording an answer snapshot, requesting takeover, marking an unsupported task, starting review, and submitting. Reuse the general browser tools. Do not encode LMS-specific completion logic.
  7. For browser failure, allow at most two recorded, meaningfully different recovery plans. CAPTCHA, login, physical work, CAD, and Blender pause truthfully for the student or mark unsupported; they never pretend completion.
  8. For attempt-only, verify the completed page state, persist a concise answer snapshot, transition to ready_review, notify, and start the configured review deadline while leaving the webpage untouched.
  9. For explicit auto-submit, resolve permission again immediately before submit, capture fresh pre-submit evidence, invoke the existing gated submit tool, then require fresh post-submit receipt evidence before transitioning to submitted. Ambiguity becomes needs_user.
  10. When review expires, atomically write an answer fallback Markdown artifact, attach its ID to the execution record, transition to preserved, release the lease, and continue the queue. Startup performs the same reconciliation for an expired deadline.
  11. Add a compact renderer surface showing lifecycle status, schedule, active execution, retries/handoff, review countdown, submission receipt, and fallback link. Keep the current Studi visual language; defer full dashboard work.
  12. Run a subtraction pass, focused deterministic checks for time/recovery/permission, then one official Playwright MCP user-like test of the real Electron build.

High-value cases

  • Window closes during work: process and lease survive; tray Open restores the exact task.
  • Sleep/restart across two missed wake times: one scan claim, one future next-run.
  • Attempt-only: completed answers stay in the page and review timer starts.
  • Review expires: answer Markdown exists and is linked before the lease is released.
  • Auto-submit: fresh assignment-level permission plus pre/post evidence yields one verified receipt.
  • Ambiguous confirmation, CAPTCHA, expired login, unsupported work, or two failed recovery plans ends in an honest handoff/failure with no queue deadlock.

Explicit exclusions

  • No full weekly dashboard, tutoring, learning sessions, Clerk, Convex, PostHog, billing, packaging, updater, or multi-device coordination.
  • No generic cron engine, distributed job queue, workflow DSL, plugin framework, or LMS-specific executor.
  • No CAD, Blender, or physical-assignment automation.
  • No real school submission during testing without the student's explicit task-specific authorization. Use a controlled local page to prove the destructive submit boundary.
  • WP-07 remains implemented but unverified until the student completes its real Moodle sign-in handoff; this package cannot manufacture that evidence.

Integrated app test

Launch the production Electron build with loopback CDP and drive the renderer using the official Playwright MCP. Exercise close/hide/restore, pause/resume scheduling, one controlled assignment through review timeout and fallback, one controlled explicit auto-submit with verified receipt, a restart during a pending timer, and a user handoff. Inspect persisted receipts after each boundary. Native tray/notification OS surfaces may use deterministic Electron receipts when Playwright cannot reach them; do not substitute generic computer control.

Pass conditions

  • Only one app instance and one browser worker exist; closing the window neither quits nor cancels work.
  • A due schedule is claimed once, runs hidden, and survives sleep/restart without duplicate scans.
  • Notification activation restores the intended task or scan state.
  • Attempt-only never submits. Explicit auto-submit requires fresh resolved permission and verified post-submit evidence.
  • Review expiry writes and links a readable Markdown fallback before the queue continues.
  • Every required case ends in a truthful task/execution state with retained page, event, receipt, or file evidence.
  • Focused tests plus typecheck, build, contracts, storage, agent, Electron, foundation, and protected Sites gates remain green where relevant.
  • One read-only reviewer rates the green implementation at least 8/10 for clarity, directness, maintainability, and lack of unnecessary code.

Fail conditions

The package fails if closing the window stops work, a missed schedule runs twice, restart repeats a submit, attempt-only reaches a submit tool, a click is labeled submitted without post-submit proof, timeout releases the task before saving answers, unsupported work is claimed complete, or new infrastructure exists only for hypothetical future behavior.
