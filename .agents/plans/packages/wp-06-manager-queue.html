WP-06 · verified implementation dossier

One durable manager owns what runs next.

This package turns stored assignments, rules, preferences, memories, and Pi sessions into a restart-safe queue. It does not scan an LMS or complete an assignment yet. Read the verified conclusion or walk through the code.

Observable outcome

Studi can queue eligible assignments by deadline and priority, steer one task to the front, lease exactly one browser-driving worker, cancel work, and resume the same ordering after the local store is reopened. A real Pi manager turn can inspect and steer that queue through narrow Studi tools.

State and ownership

  • The Electron main process owns one ManagerCoordinator.
  • SQLite owns durable queue entries, priority, lease state, worker session linkage, and confirmed pattern matches.
  • The existing task event stream remains the source of task state.
  • Pi owns session transcripts. One manager session is long-lived; assignment workers are explicit child sessions.
  • Markdown preferences are injected every manager turn. Scoped Markdown memories are retrieved separately and labeled as memory.

Core data shape

A queue entry binds one task to its course, due time, priority, enqueue time, resolved permission, optional confirmed pattern match, and optional lease. A lease has one worker/session identity and one lifecycle state. The coordinator derives the next item from durable rows rather than keeping a second in-memory queue.

Permission resolution must build its pattern context from repository-owned confirmed matches. The agent cannot assert a pattern ID in a tool call.

Implementation sequence

  1. Add the smallest versioned SQLite records needed for queue entries, confirmed assignment-pattern matches, and the single active worker lease.
  2. Add a coordinator that resolves stored permissions, rejects do_not_attempt, orders queued work by manual priority then deadline, and atomically acquires/releases the one lease.
  3. Support enqueue, steer-next, cancel, start-next, finish, and reopen recovery. A crashed active lease returns to queued work unless the stored task state says otherwise.
  4. Create one persistent manager Pi session and explicit worker sessions. Do not create a generic multi-agent framework.
  5. Give the manager narrow queue inspection and steering tools. Do not give it raw SQL, filesystem access, or authority to invent permission provenance.
  6. Load global preferences on every turn. Retrieve only explicitly scoped memories requested by the coordinator and keep their prompt sections distinct.
  7. Expose a minimal Electron/renderer control to run a real manager turn and show the queue before and after steering.
  8. Run a subtraction pass and remove any wrapper, table, or test that does not protect this outcome.

Current risks worth proving

  • Equal deadlines still follow explicit manual priority.
  • A permission change while queued is re-resolved before lease acquisition.
  • Two start attempts cannot own the browser lease together.
  • Reopening SQLite produces the same next item and recovers a crashed lease.
  • Manager compaction or session replacement does not change durable queue state.

Deliberately excluded

  • LMS discovery, course scanning, and pattern clustering. WP-07 owns those.
  • Browser completion, takeover, submission, timers, and fallback answers. WP-09 owns those.
  • Tray scheduling and native notifications. WP-08 owns those.
  • A general job runner, distributed queue, multiple browser workers, or plugin system.
  • Model-written permission rules without explicit user confirmation.

Pass conditions

  • Focused deterministic checks prove ordering, permission refresh, single leasing, steering, cancellation, crash recovery, and reopen equivalence.
  • The desktop app runs one real Codex-backed Pi manager turn that reads the durable queue and performs a safe steering action through Studi tools.
  • A tester closes and reopens the app, observes the same durable next task, and confirms a second worker cannot start while the first lease is active.
  • Contract, storage, agent, Electron, and protected Sites gates remain green where the changed boundary reaches them.
  • The reviewer finds no concrete blocker in elegance, traceability, or maintainability.

Fail conditions

WP-06 fails if queue order lives only in memory, preferences and memories share an undifferentiated prompt blob, the agent can assert pattern provenance, permission changes are ignored at start time, two workers can lease the browser, or the real run is replaced with a fake.
