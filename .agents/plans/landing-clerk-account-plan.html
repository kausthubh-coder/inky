01 · Outcome and decisions

The website is the front door. The desktop is the room.

A visitor can join the beta, return later, sign in, see whether their seat is ready, manage their plan, download or open Studi, and finish the same account sign-in inside Electron without entering credentials twice.

Decision

Clerk is the account source

Clerk owns identity, waitlist status, invitation, browser sessions, and user subscriptions.

Decision

Convex is the app projection

Convex keeps the small set Electron needs: approval, entitlement, credits, usage, active device, and billing event receipts.

Decision

Electron stays public

No client secret ships in the app. OAuth uses Authorization Code with S256 PKCE, state, nonce, and a one-shot loopback callback.

Design

Use the floating nav island

Adopt .agents/.design/landing-nav-island.html. Inky sits beside the wordmark. Signed-out visitors see "Sign in" and "Save me a seat". Signed-in users see "Dashboard" and their avatar.

Replace

Do not keep two live waitlists

The current public Convex email mutation becomes a legacy import path. The new form uses Clerk's custom waitlist flow, so invite state and the email the visitor entered cannot drift apart.

02 · Current audit

Most of the hard pieces exist, but they do not meet yet.

Landing

  • Next 15 and Clerk 6.36.5 are installed.
  • ClerkProvider exists but there are no sign-in, account, or protected dashboard routes.
  • The waitlist writes email directly to Convex.

Desktop auth

  • PKCE already creates 256-bit verifier, state, and nonce values.
  • The loopback callback validates state and is single-use.
  • ID tokens are verified against issuer, audience, signature, and nonce.

Entitlements

  • Convex already stores beta access, plan, credits, and one active device.
  • Plans are hand-managed as beta or supporter.
  • No Clerk Billing events update this state yet.

Visible demo problems

The title bar contains "This week," which makes the fake desktop feel like a website. The dock icon depends on /icon.svg as a CSS background, so it can disappear or crop badly. The first two beats jump from a joke to one problem set without explaining the daily scan or saved-answer flow.

Protected-route gap

The landing root should stay public. /dashboard, /settings, and /billing need server-side protection. API and webhook routes need separate rules, with webhooks verified by signature instead of a browser session.

03 · User journeys

Four small journeys cover the whole account lifecycle.

New visitor
Landing→Email→Clerk waitlist→Confirmation

Keep the current inline form and Inky voice. Add "Already have a seat? Sign in." Duplicate submissions resolve to the same successful state.

Approved student
Invite→Create account→Dashboard→Download / open Studi

The dashboard leads with one next action, not analytics. Seat status, desktop connection, plan, and recent usage sit below it.

Desktop connection
Open Studi→PKCE→Browser session reused→Electron approved

The browser may already know the Clerk user, but Electron still generates and verifies its own OAuth transaction.

Billing
Dashboard→Billing→Clerk checkout/profile→Webhook→Convex projection

Clerk shows payment methods, invoices, and plan changes. Convex consumes signed events and updates Electron's entitlement.

06 · Browser-to-desktop PKCE

The landing helps the handoff. It never handles the verifier.

1Landing opens Studi

/connect/desktop launches a registered studi://connect link. If the app is missing, the page shows the Windows download and installation help.

2Electron starts the transaction

Electron generates a fresh verifier, S256 challenge, state, and nonce. It starts a loopback listener and opens Clerk's authorization endpoint in the system browser.

3Clerk reuses the web session

If the student is already signed in on the landing, authorization is quick. Clerk still owns the consent and account boundary. The landing never copies a session token into the deep link.

4Loopback receives one code

Use one registered loopback URI strategy that Clerk accepts. Prefer a fixed high port for predictable allowlisting. If Clerk supports RFC 8252 loopback port matching for this OAuth app, keep the ephemeral port and prove it in a live development test.

5Electron exchanges and verifies

The token request includes the verifier. Electron verifies issuer, audience, signature, expiry, and nonce, then calls Convex with the fresh identity token.

6Convex decides access

Convex returns approved, waitlisted, device conflict, or billing-required. The browser dashboard and desktop show the same status because both read the same projection.

Configuration gate

In Clerk, the Studi desktop OAuth application must be public and PKCE-required. Register the chosen loopback redirect URI exactly, keep the current client ID in environment-specific configuration, and never add a client secret to Electron.

07 · Data and event contracts

Project Clerk into one small account record.

accountProfiles

clerkSubject, email, display name, waitlist state, approved at, plan slug, subscription state, credits, updated at.

One row per Clerk subject. This replaces split reads across accounts, betaAccess, and entitlements after a safe migration.

clerkEventReceipts

Clerk event ID, type, received at, processed at, and sanitized failure category.

The event ID is unique. Replayed webhooks return success without applying the change twice.

Waitlist events

Joined, invited, accepted. Historical Convex emails get a one-time controlled import or remain legacy-only.

User events

Created, updated, deleted. Deletion revokes approval and active-device access without erasing local schoolwork.

Billing events

Subscription active, updated, past due, and ended. The projection changes only after signature verification.

Dashboard query

Return a purpose-built view model: greeting, access status, plan name, credit or usage summary, desktop connection state, download build, and the primary action. Do not expose raw webhook payloads, device secrets, or Clerk metadata.

10 · Verification

Prove the seams, not just the pages.

Unit and contract

  • Waitlist states and validation.
  • Route protection.
  • Webhook signatures and replay safety.
  • Account projection transitions.

PKCE boundary

  • Keep current entropy and S256 tests.
  • Add redirect allowlist and fixed-port behavior.
  • Prove wrong state, wrong nonce, reuse, timeout, and revoked refresh token.

Browser pass

  • Public landing and mobile nav.
  • Join, sign in, waiting dashboard, approved dashboard.
  • Settings and billing in Clerk's development gateway.

Studi feature pass

Use the project's test-studi skill for the packaged Electron handoff. Reuse the dedicated QA profile. Never use the everyday Studi profile, never expose the authorization URL, and stop before a real school submission.

11 · Release gate

Ship only when these statements are true.

Account truth

  • Clerk is the only live waitlist.
  • Every dashboard and Electron access state agrees.
  • Billing webhooks are verified and idempotent.
  • Legacy beta users keep their access and device binding.

Auth boundary

  • Electron contains no OAuth client secret.
  • PKCE is required in Clerk.
  • The exact loopback redirect works in development and packaged Windows.
  • The landing does not place Clerk tokens in a deep link or URL.

Visible product

  • Floating island nav matches the approved design.
  • Signed-in and signed-out nav states are clear.
  • The Inky introduction uses the new script.
  • "This week" is gone from the title bar and the app icon renders.

Operations

  • Development and production Clerk settings are documented separately.
  • Webhook secret and production keys live only in deployment secrets.
  • A rollback can disable billing projection without blocking existing beta users.
  • Support can identify waiting, approved, past-due, and device-conflict accounts.
