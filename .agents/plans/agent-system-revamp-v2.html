01 · The design test

What survives if none of today's code existed?

The architecture is based on product facts, not today's classes: one student-facing character, several kinds of work, one visible school page, local memory, explicit submit authority, and expensive model calls.

Keep

  • One conversation surface that can show home or one assignment conversation.
  • One transcript per durable subject, seeded by a brief rather than another transcript.
  • Capabilities composed from the job state and policy.
  • One note shape queried by scope and purpose.
  • A deterministic harness that loads the exact product packs.
  • Permissions and browser evidence outside model-written prose.

Change from the prior draft

  • Sends are addressed; main does not infer their target from "foreground" flags.
  • Assignment conversation exists before assignment work.
  • Only explicit start acquires the browser and adds action tools.
  • Scan is a run controlled by typed taps, never a free-chat target.
  • Capability packs are reusable units; job packs compose them.
  • Home knowledge survives as notes, not by relying on an infinite transcript.
Language: "job," "capability," "claim," "pack," and "session" are implementation terms only. The UI says Inky, this week, the assignment, the page, and your work.

04 · Domain shape

Conversation, job, run, and browser claim are different facts.

ConversationTarget =
  | { kind: "home" }
  | { kind: "assignment", assignmentId }

JobKind = "home" | "scan" | "assignment" | "tutor"

Job = {
  jobId, kind, subjectId,
  phase: "idle" | "running" | "waiting" | "finished" | "cancelled" | "failed",
  sessionPath, turnIndex, createdAt, updatedAt
}

AssignmentExecution = {
  assignmentId, jobId,
  phase: "queued" | "working" | "needs_user" | "ready_review"
       | "submitting" | "submitted" | "preserved" | "cancelled" | "failed",
  reviewDeadline, submissionAttemptedAt, answerArtifactId, submissionReceiptId
}

Run = {
  runId, jobId, turnIndex, assignmentId?,
  trigger: "send" | "start" | "resume" | "scan_tap" | "scheduled",
  state: "running" | "waiting" | "completed" | "failed" | "aborted",
  startedAt, endedAt?
}

BrowserClaim = {
  jobId,
  purpose: "scan" | "assignment",
  state: "acquiring" | "active" | "yielded",
  acquiredAt
} | null

Conversation is where text goes. Home and assignments have conversations. Job is durable agent/session identity. Assignment execution retains the detailed safety lifecycle. Run is one persisted model/tool loop triggered by a send, start, resume, scan tap, or schedule. Effects and authorization bind to its id and turn index so restart cannot reuse them across runs. Browser claim is exclusive authority over the visible page. These are related aggregates, not aliases. Submission, failure, and preservation facts do not collapse into a generic job status.

One state owner: a job repository owns phase/session/turn state; one browser-claim repository owns exclusivity. The renderer never mirrors these as independent mutable booleans.

Tool attachment rule

toolsFor(job, policy, claim) {
  if (job.kind === "home") return HOME
  if (job.kind === "scan" && claim.jobId === job.jobId) return SCAN
  if (job.kind === "assignment" && claim.jobId !== job.jobId) return ASSIGNMENT_TALK
  if (job.kind === "assignment") return policy.maySubmit ? ASSIGNMENT_WORK_SUBMIT : ASSIGNMENT_WORK
  throw TutorNotAvailable
}

This is a registry over concrete current capabilities, not an extension framework. Each capability owns its instructions, tool definitions, and the boundary it is allowed to call. A send never starts work merely because its target is an assignment. Only the typed start operation, direct from the button or invoked by the home start tool for an explicit command, can acquire the claim.

The unique key makes "upsert the current CSC 316 project" a real operation instead of appending a new course note every week. Examples: course/csc-316/work/current-project, pattern/webassign-weekly/how-to/execution, assignment/a-42/work/leftover.

JobAutomatic briefSearchable, not dumped
HomeSmall student preferences, queue summary, active jobsAllowed school/course/assignment notes when the student asks
AssignmentStudent preferences; all bounded current course notes; notes for confirmed pattern matches; this assignment note; fresh gate; folder listing; last browser receipt; linked systemsOlder assignment notes in this course and allowed pattern notes

  • note_search and note_read are jailed to the job's allowed note scopes.
  • Pattern notes load from the same repository-confirmed pattern matches used by permission resolution. A title/URL similarity may propose a match later; it cannot silently become one.
  • Notes are model-written hints. They cannot change permission, claim the browser, create verified school rows, or satisfy evidence.
  • Markdown bodies stay in app data; SQLite stores the validated index. No HTML, cookies, auth headers, tokens, page dumps, or answer payloads.
  • No embeddings in this release. Exact indexed scopes plus bounded keyword search are enough.

Migration

One versioned migration converts preferences, memories, and answer metadata to notes where meaning is recoverable. The existing scan workflow is split: prose navigation hints become a school scan note, while replayable structured steps become a versioned school-scan workflow owned by the scan service. Answer fallback files remain student-facing files and gain assignment-note metadata. Unknown legacy artifacts are backed up and reported, never guessed into a scope. After verified migration, the four-kind artifact API and raw memory picker are deleted; the workflow remains a domain object, not a drawer kind.

Crash consistency: validated Markdown is authoritative and written by atomic rename. The SQLite note index is a rebuildable cache containing revision and content hash. Startup and failed-write recovery rescan the notes tree, remove orphaned index rows, and index valid files that committed before a crash. The index is never treated as proof that a missing body exists.

08 · Work

One visible page, one claimant, explicit start.

student starts assignment or scan→ main checks conflict→ fresh policy→ claim persisted→ capabilities attached→ Pi turn→ receipt + job phase
  • A scan start fails or queues while an assignment is working, waiting, in review, or submitting. An assignment start fails while a scan owns the page. This retains the current single-browser law.
  • Takeover yields automation but does not transfer the claim to another job. Resume re-observes and restores action tools only after the return predicate is verified.
  • Assignment messages are multi-turn on the same job. A new turn rebuilds a fresh brief and policy, reuses the transcript, and reattaches current capabilities.
  • Pi compaction controls transcript size. Durable facts are written as notes; no product behavior depends on old transcript text surviving compaction.
  • browser_submit is attached only when the fresh SQLite resolver returns auto_submit, and the existing current-conversation confirmation/evidence gate still applies.

Mutating-tool effects

Every browser/file/shell/app mutation gets an effect id bound to runId + turnIndex + toolCallId. Main persists intent plus expected page/file revision before invoking the tool, then persists its receipt. If the process stops between effect and receipt, recovery re-observes the real page or file. It records success when the expected postcondition is visible, retries only when non-application is proven, and hands off when ambiguous. Interrupted shell commands are never automatically replayed: after process cleanup and file re-observation they enter needs_user unless a narrow tool-specific postcondition proves completion. A browser claim prevents concurrency; the effect journal prevents blind replay and cross-run receipt reuse.

Submission authorization is a host fact

Typing "submit it" makes Inky present the existing explicit confirmation control; it does not itself attach or invoke browser_submit. The student's confirmation action creates a one-use SubmissionAuthorization bound to assignment id, job id, run id, turn index, fresh gate revision, and fresh browser control revision. Main consumes it atomically when starting submission. Missing, stale, mismatched, or already-consumed authorization is rejected before any page action. Model text and model-supplied tool arguments cannot create this fact.

Files, shell, and connected apps

The full revamp includes these assignment-only capabilities. File tools are resolved below the student-selected homework root; absolute incoming paths, traversal, and symlink escape fail closed. The course note may point to the living project. A generic subprocess is not "jailed" merely because its cwd is inside that root. Shell execution ships only after a Windows OS-enforced sandbox proves the homework root is its sole writable mount and the required build tools work. If that spike fails, this release keeps bounded file tools and marks shell unavailable rather than claiming confinement it does not have. Connected-app tools come from a user-scoped Composio session and appear only after the student connects that toolkit. None of these capabilities appears in home, scan, or assignment conversation before start.

09 · Composio connected apps

The Composio project key stays on the server.

Composio is installed and its project key is configured only in the untracked local environment and Convex development environment. Exact tool metadata now passes for GitHub repository listing, Gmail thread/message reads, Notion search/page reads, Google Drive find/download, and Google Docs structured/plain-text reads. The dedicated QA identity has an active GitHub connection; the other providers still require their own student OAuth handoffs.

Secret and identity ownership

  • Use @composio/core in a Convex action or Vercel server function. Never bundle the Composio project key into Electron, preload, renderer, the headless harness, diagnostics, or telemetry.
  • Development reads COMPOSIO_API_KEY from the untracked local/server environment. Production reads the same name from the server's encrypted environment.
  • Use the stable Clerk subject as Composio userID. The server derives it from the authenticated request; Electron cannot supply another user's id.
  • A connected account belongs to that user and toolkit. Composio stores and refreshes the provider token.

Assignment tool boundary

  • Create a Composio session scoped to the current user and an explicit toolkit/action allowlist.
  • Pin toolkit versions. A catalog update cannot silently change a production tool schema.
  • Map allowed Composio schemas into Studi tools. Execute calls through the server session and return the typed result to the local job trace.
  • Connection setup uses a Composio Connect Link in the system browser. The callback server verifies the signed-in Clerk user before activating the one-time session_uri.
  • Connected apps never create permission, claim the school browser, submit schoolwork, or become available to home and scan jobs.

How we test Composio

  1. With no key, fixture and contract tests prove the app reports Composio as unavailable and exposes zero connected-app tools.
  2. Before AR-08 live work, the user adds COMPOSIO_API_KEY to .env.local and the Convex development secret. The value never goes into chat or a tracked file.
  3. bun run test:composio -- probe calls the server boundary and reads project/toolkit metadata without connecting a user account or executing a tool.
  4. A dedicated test account completes one Connect Link. The callback must reject a mismatched Clerk subject and a reused or expired session_uri.
  5. The headless agent harness runs one read-only tool through the real server broker, records its full non-secret arguments/result and usage, then proves a tool outside the allowlist is absent.
  6. test-studi opens Settings, connects the same dedicated toolkit through the system browser, starts a fixture assignment, and observes one harmless read-only tool result in the desk trace.
  7. Expired/revoked connection, provider failure, timeout, and cancellation return a useful job state and telemetry event. They never expose the project key or provider token.

Current Composio sessions scope tools and connections by stable user id, and session execution keeps the tool router context. Direct tool execution requires an explicit toolkit version. See Composio authentication, sessions, and TypeScript tool execution.

10 · Runtime boundary

Production and tests use the same host, with different adapters.

Production Electron

The shipped runtime remains Pi AgentSession with the openai-codex ChatGPT provider. Electron supplies SQLite, the visible school browser, secure auth, notifications, and telemetry adapters.

Headless default

A scripted driver and fixture adapters exercise jobs, turns, tools, persistence, restarts, and traces without Electron, a model call, or a real school account.

Headless live check

An opt-in pi-codex driver creates the real Pi session against the same packs and fixture tools. It proves Inky can reason through one safe case without opening the app.

JobModelDriver = {
  id: "scripted" | "capture" | "pi-codex"
  probe(): { available, authenticated, reason }
  createSession(turn, tools, signal): AgentSession
}

This is the only driver seam. It already exists in spirit as AgentSession and the Pi model runtime. The revamp makes it job-shaped and moves it behind the pure host. There is no Cursor, Claude, OpenCode, MCP, or generic provider framework in this plan.

Credential checkpoint

  1. scripted and capture never need auth and are the normal package gates.
  2. pi-codex is opt-in. It probes the isolated QA Codex cache before creating a session or spending usage.
  3. The harness may read the gitignored .agents/studi-qa/codex-auth/auth.json only through the existing QA import helper. It never reads everyday Studi userData.
  4. If the provider reports needs_login or usage exhaustion, the live check is pending. The deterministic gates continue, and no fake ready state replaces the missing proof.
  5. Auth bytes, device codes, cookies, tokens, provider credentials, and real student profile paths never enter terminal output or run records. Fixture note bodies, page content, assignment answers, and non-secret tool payloads are retained so the harness can prove exact behavior.

13 · Product and agent telemetry

Track the full Inky loop, not a handful of finish events.

Analytics and replay default on for the private beta. The shared trace now records ordinary product content, Clerk/user/device context, model and reasoning, token and cost totals, turn and tool timing, tool arguments/results, queue transitions, errors, and connected-app activity while credentials remain excluded. Renderer autocapture covers named clicks, changes, and submits, and Web Vitals are enabled. A PostHog personal read key or signed-in analytics browser is still required to audit the remote project from outside the app; the capture token cannot query events.

Content policy

When analytics is enabled, Studi does not run a general-purpose redactor over product content. User messages, Inky replies, assignment titles and answer text, note bodies, URLs, prompts, tool arguments/results, and error details are recorded so we can reconstruct what happened. Field size limits are explicit: if PostHog cannot accept a complete value, the event records original byte count, retained byte count, content hash, and truncated=true. It never silently clips a value.

Credentials are not product telemetry. Password fields, cookies, auth headers, access/refresh tokens, OAuth codes, device codes, Clerk tokens, the Codex auth cache, the Composio project key, provider credentials, and secure-storage bytes never enter a telemetry event. Code excludes these values at the boundary where they are created or typed. A final secret-canary guard remains as defense in depth, but it does not remove ordinary messages, answers, notes, URLs, tool payloads, or user metadata.
  • Every job event has traceId, monotonic sequence, jobId, runId, and turnIndex. PostHog can rebuild one turn without guessing across coordinator events.
  • The job host emits events once. The PostHog sink, local inspector, diagnostics exporter, and headless harness subscribe to the same typed stream.
  • The harness uses an in-memory telemetry sink and writes the full fixture trace to run.json. It never sends test events to PostHog.
  • Analytics remains enabled by default for the private beta. Turning it off stops new remote events. Replay remains a separate setting.
  • Production sends every private-beta event at 100 percent sampling until volume forces an explicit change.

Telemetry proof

  1. A fake PostHog client asserts exact events and person properties for app start, onboarding, addressed sends, job/claim changes, model turns, every tool call, notes, Composio, errors, and finish.
  2. A harness session runs two turns with tools and restart. The recorded sequence must join user text, prompt, reply, tool input/result, token usage, cost, model, reasoning, and timings under one trace id.
  3. Ordinary content canaries survive byte-for-byte. Credential canaries from password, cookie, token, device-code, and Composio-key boundaries produce zero matches in the PostHog client, inspector, diagnostics, and harness record.
  4. Missing usage is stored as null with usage_available=false, never as zero. Cumulative totals must equal the sum of turn events.
  5. test-studi runs onboarding and one fixture assignment, then checks the local inspector and PostHog test project for the same ordered events without exposing any credential value.
