01 · Outcome and boundary

The beta proves one complete loop.

A permitted tester signs in, connects a school portal, watches Studi discover real work, teaches it repeating preferences, asks it to complete an eligible assignment in the visible embedded browser, handles any human-only step, and gets either a submitted result or a recoverable review artifact.

P1 outcome

Real, not scripted

The dashboard is populated only by verified browser evidence. A zero-result or partial scan stays incomplete; it never swaps in demo assignments.

Primary user

You + invited friends

Windows first, one primary computer and one active school browser profile per account. Clerk approval gates sign-in even if the installer leaks.

Runtime

Local agent, local school state

A real Pi AgentSession owns the continuous manager thread. The tester brings supported provider authentication during beta.

After P1

Intentionally deferred

Tutoring and learning sessions, the website and billing, macOS packaging, multi-device coordination, broad OS control, Gmail/docs/slides integrations, managed Studi inference, and production credit enforcement.

Permission model

Do not attempt · attempt · auto-submit

The student sets a global default, then course, repeating-pattern, and individual-assignment overrides. The most specific rule wins. Submission is a separate gated capability.

02 · Settled decisions and validation assumptions

What is fixed, and what must be proven.

Settled

Product behavior

  • One manager agent receives every user instruction.
  • Queue eligible work by deadline; the student may redirect it.
  • The desk/sidebar appears only while Studi is working.
  • Human handoff can wait 5–30 minutes, then continue with other work.
  • Ready-to-submit notification uses a configurable timer, initially five minutes.
  • If the timer expires, preserve answers as Markdown and continue.
  • Two distinct execution retries, then needs you.
Must validate

Technical spikes

  • Pi can create a real AgentSession with a tester-supported authenticated provider on a clean Windows install.
  • Electron CDP can robustly snapshot and interact with the same WebContentsView the user sees.
  • Clerk public OAuth + PKCE can return safely to the desktop app and mint the Convex-compatible token.
  • The chosen SQLite driver packages and rebuilds reliably with Electron 37.
  • PostHog replay can be bundled locally and restricted to Studi's renderer only.
  • A signed installer is deferred, so Windows SmartScreen friction is accepted for the private beta.
Rule: a validation spike may change the mechanism, but it may not silently remove the user-visible behavior. If a spike fails, update this plan and bring the alternative back for approval.
03 · Current repository audit

Discard the current app. Keep only decisions and protected infrastructure.

P1 is a clean-room implementation inside this repository. The current React dashboard, Electron shell, embedded-browser code, onboarding, Moodle scanner, scheduler, persistence, and scripted task loop are not production foundations. New code must not import, wrap, refactor, or copy those modules.

What survives

  • The approved product decisions and Q1–Q85 record.
  • The approved visual direction: cream paper, hand-drawn dark borders, Shantell Sans headings, Nunito Sans body, and the course-color palette.
  • The master plan, implementation dossiers, evidence ledger, and verified-build-loop skill.
  • The repository itself, package history, and source-control history.
  • .openai/hosting.json, worker/index.js, scripts/prepare-sites-build.mjs, and tests/sites-worker.test.mjs stay untouched.

What is rebuilt from zero

  • React UI and state projection in src/.
  • Electron main process, preload bridge, window/browser lifecycle, tray, scheduler, and notifications.
  • Real Pi session runtime, manager and worker agents, event-sourced task engine, and permission resolver.
  • General CDP browser controller and every agent-visible browser tool.
  • SQLite and Markdown persistence, Clerk, Convex, PostHog, packaging, recovery, and all test fakes.
  • No Moodle-specific production path and no migration of prototype JSON state.
Clean-room guardrail: old app files may be inspected only to identify protected repository constraints or confirm that the new build no longer imports them. They are not behavioral specifications. The approved plan, interview record, and visual direction are the specifications.

06 · Agent, browser, IPC, and cloud contracts

Small contracts keep the system replaceable.

AgentRuntime

createManager(context) → sessionId
runAssignment(taskContext) → AsyncEventStream
steer(sessionId, userMessage)
abort(runId)
compact(sessionId)
checkProvider() → ProviderStatus

Production implementation uses a real Pi AgentSession. Tests use a deterministic fake that emits the same event stream.

BrowserController

open(sessionId, url)
snapshot(tabId, options) → PageSnapshot
act(tabId, action, expectedRevision)
waitFor(tabId, condition, timeout)
captureEvidence(tabId, purpose)
requestTakeover(taskId, reason)

Every mutation includes taskId, runId, tabId, idempotencyKey, and expected page revision.

PermissionResolver

resolve(assignment, context) → {
  mode: "do_not_attempt" | "attempt" | "auto_submit",
  matchedRuleId,
  rationale,
  maySubmit
}

Only this service can authorize the browser_submit tool. The agent cannot raise its own permission.

Event envelope

{
  eventId, aggregateType, aggregateId,
  runId, sequence, occurredAt,
  schemaVersion, type, payload
}

Events are written before UI projection. Subscribers may replay safely; external effects carry idempotency keys.

Agent-visible browser tools

browser_tabsList active tabs and stable IDs.
browser_openNavigate or create a page in the one school profile.
browser_snapshotReturn URL, title, accessibility/DOM refs, forms, focus, and revision.
browser_clickClick a snapshot ref; reject stale revisions.
browser_typeType into a ref with replace/append semantics.
browser_selectSelect one or more options.
browser_pressSend a restricted keyboard action.
browser_uploadAttach a user-approved local file.
browser_waitWait for URL, text, selector/ref, or network idle.
browser_evaluateRead-only, time-bounded extraction; disabled for arbitrary mutation.
browser_takeoverPause run, focus page, notify student, verify return condition.
browser_submitSeparate policy-gated effect with pre-submit evidence.
Interaction strategy: use accessibility/DOM references first, re-snapshot after navigation or DOM replacement, and use screenshot coordinates only as an explicit fallback with before/after evidence. Chrome DevTools MCP supplies the behavioral reference; Vercel agent-browser supplies efficient snapshot/ref and session-lifecycle ideas. Studi owns its smaller contract.
07 · State machines and recovery

Every pause and failure has an explicit next state.

Assignment task

discoveredEvidence normalized; permission unresolved.
ignored / queuedRule excludes it, or deadline queue accepts it.
workingLease held; agent + browser events streaming.
needs_userLogin, CAPTCHA, ambiguity, unsupported action, or retry exhaustion.
ready_reviewWork remains in page; review timer running.
submitted / preservedVerified submit, or Markdown fallback saved and queue continues.

Run recovery rules

InterruptionPersist before effectRestart behavior
App closes during a tool callIntent event + idempotency keyRe-snapshot page; reconcile whether effect happened before retry.
Browser navigates unexpectedlyLast stable snapshot revisionClassify login, popup, blocked page, or ordinary redirect; recover or hand off.
Model/provider disconnectsPi session ID + task stateOne transport retry, then pause task without losing browser page.
User takes overHandoff reason + return predicate + expiryVerify predicate before resuming. If expired, leave task needs user and work next queue item.
Review timer expiresReview deadline + latest answer evidenceWrite atomic Markdown fallback, attach it to task, leave webpage as-is, continue queue.
Scheduled scan overlaps active workRun leaseQueue scan; never drive the same browser concurrently.
08 · End-to-end journey traces

The implementation is designed around causal flows.

A · Sign in and entitlement

Renderer requests sign-in→Main opens system browser→Loopback callback verifies state + PKCE→safeStorage encrypts refresh token→Convex client receives Clerk JWT→betaAccess permits app

B · First school scan

Agent asks for school URL→Persistent browser opens→User signs in→Agent verifies session→General browser tools inspect courses + assignments→Third-party systems trigger handoffs→Coverage ledger commits→Dashboard projects verified rows

C · Complete an assignment

Deadline queue selects task→Permission resolver allows attempt→Worker receives assignment + course preferences→Tool calls mutate visible page→Evidence verifies answer state→Review notification→User submits or fallback Markdown is saved

D · Discover a repeating pattern

Scans cluster similar assignments→Agent proposes a named pattern→User chooses permission→Rule is stored separately from memory→Future assignments match deterministically→User can edit in Settings

12 · Security, privacy, and telemetry

Observe the product, keep secrets and the school page local.

Never leave the device

Passwords, cookies, refresh tokens, authorization headers, school page HTML, school-browser replay/screenshots, assignment answers, local rules, memories, workflows, queues, and Pi session transcripts.

Allowed in private beta

Clerk user ID, name, email, student name, school URL, course and assignment titles, model, reasoning effort, durations, token counts, estimated cost, error messages after secret stripping, Studi renderer replay, and feedback the user explicitly sends.

Outbound architecture

All telemetry and Convex writes pass through typed DTO builders. Builders use field allowlists rather than object spreading. Secrets are stripped; consented personal and school facts are stored. The school WebContentsView never loads PostHog code. Pi prompts and answers remain local.

13 · P1 release gate

“Almost deployable” has a concrete meaning.

Blocking capabilities

  • Approved Clerk account signs in and unapproved account cannot.
  • Real Pi AgentSession works without Codex CLI.
  • Persistent visible browser survives restart.
  • Real scan populates dashboard with provenance.
  • Rule hierarchy and repeating-pattern confirmation work.
  • Supported assignment reaches truthful terminal state.
  • Review expiry creates readable Markdown.
  • Tray/schedule/notification recovery works.
  • PostHog secret-strip canaries pass.
  • Clean Windows install passes.

Accepted limitations

  • Private beta, Windows only.
  • Unsigned installer may show SmartScreen warning.
  • One computer/profile/browser-driving task.
  • Physical, CAD, Blender, and unsupported workspace tasks hand off.
  • Tutoring and learning sessions absent.
  • Tester-provided model authentication.
  • School UI changes can break a workflow; evidence and diagnostics make the breakage visible.
14 · How the AI coding loop uses this plan

Approve the frontier, then execute it.

  1. Master-plan review: revise this artifact until you say the architecture and package graph are approved.
  2. Frontier selection: choose every package whose dependencies are verified. Initially WP-00 only; after WP-01, multiple lanes open.
  3. Just-in-time dossier: the skill expands each chosen package into exact files/modules, interfaces, fixtures, commands, pass/fail cases, and expected evidence.
  4. Your approval: change the dossier until it matches what you want. No implementation begins before approval.
  5. Implementation loop: baseline → contract test → smallest vertical slice → targeted test → review → integration gate → evidence.
  6. Failure rule: two distinct approaches to the same blocker, then preserve evidence and ask for the missing decision instead of retrying forever.
  7. Integration: shared contracts, migrations, and release gates are owned by one lane.
  8. Conclusion: after WP-15, create an HTML explanation that traces sign-in, scan, task, browser tool, handoff, submission, recovery, and telemetry through the code in execution order.
