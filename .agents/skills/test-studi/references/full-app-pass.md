# Full app pass

Use for a requested end-to-end test, release readiness, onboarding changes, or changes spanning several production systems. This is a connected student journey, not a collection of seeded screens. Follow the entrypoint's isolation rules and record the exact build. Use a fresh named profile for onboarding and retain it for restart; preserve other QA profiles.

## Journey and independent observations

1. **Admission and setup.** Follow [onboarding-pass.md](onboarding-pass.md). Complete dedicated development account sign-in/invitation, approved admission, provider connection, homework folder, school URL and permission selection using visible controls. Verify persisted values. If a boundary fails, diagnose it without seeding a success state; continue unrelated checks.
2. **Discover and start a scan.** From the normal landing screen, find the scan action without a supplied click script. Note ambiguous controls as usability findings. Run the real provider against the local school fixture; verify visible progress and compare discovered course, assignment, dates and instructions to fixture ground truth. A green badge alone is insufficient.
3. **Needs help and recovery.** Exercise a supported fixture login/expired-session handoff or another controlled recoverable interruption. Verify Inky explains what happened, the primary action opens the right activity, and continuing actually resumes the scan. Keep the fixture mechanism explicit; do not invent support in the small fixture. Record missing scenario coverage and use an isolated richer fixture or focused contract to supplement it.
4. **Chat and navigation.** Get a real chat reply; refer to the discovered assignment where supported. Open/collapse chat, switch views and return. Check draft/history retention and stop/retry behavior relevant to the change. A sent message is not proof of a reply.
5. **Homework and rules.** Set a scoped rule through the UI. Have the real agent read the fixture assignment and produce the requested answer/files. Independently inspect the saved artifact and fixture outcome. With attempt-only permission, prove no submission occurred. If testing submission, use a local simulated assignment with explicit submit permission and verify the fixture receipt; never submit real schoolwork. Test a representative take-over/resume or review step and preserved work.
6. **Competing activity.** While an assignment is active, try scanning and ordinary chat. Verify the product's actual concurrency contract: correct ownership, accurate busy explanation and an available next action. If offering stop-and-scan, prove it waits for cancellation/release and does not scan after a failed stop. A paused assignment after restart must offer a usable resume/open/stop path; waiting forever is not recovery. Check the reverse scan → assignment transition if affected. Closing a browser panel must not accidentally cancel work or claim to do so.
7. **Connected apps.** Where included in the tested release or requested feature, use a dedicated development/sandbox integration. Exercise connect/check, a bounded read or reversible authorized fixture task, and the common disconnected/failure recovery. Verify the result at the service, not just the agent's claim. A skipped optional integration does not fail the core school journey, but must be listed as untested; no personal account authorization, external messages or real writes are implied by this test.
8. **Return and restart.** Reopen the same profile using its new receipt. Verify access/provider state, one copy of each scanned record, saved answer/files, rules, chat and activity state. Rescan and check identities remain stable. When durable active/paused work is affected, restart during that state as a separate checkpoint and verify recovery.

Use the minimal local fixture for the core journey and the benchmark's richer fixtures only when they exist in this checkout. One course/one task is not broad LMS compatibility proof. For a release, add platform-specific installed upgrade tests when claiming updater behavior; the controlled Electron suite is not an installed update rehearsal.

## Release and combined changes

Run applicable automated suites from the current `package.json` before the integrated journey. Use `bun run test:all` for a broad release sweep when applicable, but inspect its coverage: UI logic tests and scripted harnesses do not replace visual inspection or live-provider outcomes. Investigate failures; do not hide them behind retries. Test the affected native platforms or explicitly leave those gates pending. Retest after subsequent changes only at boundaries they can invalidate.

Report core journey, optional integrations, live-model scenarios and installed-platform coverage separately. Do not call the complete release verified while a required gate remains untested.
