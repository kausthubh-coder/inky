# Web account UI pass

Use for `landing/` account UI changes. This is a real Clerk + Convex web journey, not proof of Electron onboarding or agent execution.

1. Run `bun install --frozen-lockfile` if dependencies are missing. Start this checkout with `bun run --filter landing dev`; if port 3000 belongs to another checkout, run `bun run dev -- --port 3001` from `landing/`. Verify ownership before reusing a running server. Keep configured environment values private.
2. Use isolated generic Playwright for Clerk sign-in (never the user's personal browser session). Open the local `/dashboard`, which should redirect to `/sign-in` when signed out. Verify Clerk displays **Development mode**. Reuse the dedicated QA identity and development email-code flow documented in [clerk-electron-journey.md](clerk-electron-journey.md). The web flow goes directly through `/sign-in`; it does not use the Electron launcher's claim URL.
3. Confirm the signed-in identity and observe the live access state. A waitlisted account can exercise the web dashboard. Do not change beta access or create another identity to obtain an approved screenshot. The earlier Electron admission blocker does not block a web waitlist UI pass.
4. Capture the dashboard at a recorded desktop viewport and a narrow phone viewport. Inspect the actual screenshots. Check horizontal overflow, font loading, Inky rendering, readable state, keyboard focus, and account navigation.
5. Exercise the account navigation (Home, Settings, Billing, Usage, Feedback). These tabs live inside the account page, not the site header. They stay visible at phone widths; verify they wrap without overlapping the page. Usage must show the live monthly assignments, browser minutes, agent tokens, and available credits, including zero values. Approved accounts have a single dashboard link to the desktop handoff page. For Settings changes, check Profile editing and cancel without saving, then open Security through Clerk's Account menu. Confirm the form has one outer surface and fits the viewport. Stop before submitting feedback or triggering `studi://connect` unless that action is part of the authorized test. Do not label reaching the handoff page as a completed desktop connection.
6. When other access or usage states need visual coverage, render the real presentational component with synthetic data in an isolated local fixture outside production routes. Label it as a fixture, retain the auth gate, and do not mutate live data for screenshots. A fixture does not prove live entitlements.
7. Run `bun run --filter landing typecheck` and `bun run build:landing`. Retain concise evidence under ignored `.agents/studi-qa/`: checkout/server port, viewport sizes, live state, fixture states, routes exercised, and any failures. Never retain login codes, tokens, cookies, or authorization URLs.

On 2026-09-07, the existing dedicated identity signed into the web account successfully and the live dashboard reported waitlist access. Treat that as an observation, not a required or permanent fixture state.
