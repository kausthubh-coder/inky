# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

This is a Bun workspace. Desktop UI lives in `src/`. The public site lives in `landing/`. Shared Convex stays at `convex/`. `bun run build` compiles Electron and the Vite client only. It must leave `dist/electron/main.js`, `dist/electron/preload.cjs`, and `dist/client/index.html`. Do not restore OpenAI Sites packaging.

## Durable Studi product decisions

- The local desktop app owns the product experience. The public site is a Next.js landing app in `landing/`, deployed on the Vercel project `inky` (not `studi-2`), talking to the same Clerk instance and Convex deployment. Waitlist emails are stored in Convex. Do not turn on Clerk waitlist mode; that would block Electron sign-in.
- Keep `.cursor/` at the repo root. Cursor only loads MCP and rules from there. Do not move it into `.agents`.
- Persistent QA profiles live in gitignored `.agents/studi-qa` and `.agents/studi-fresh`. Do not recreate top-level `.studi-qa/` or `.studi-fresh/`.
- OpenAI Sites packaging is gone. Do not restore `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, `tests/sites-worker.test.mjs`, or a `test:sites` script.
- Feature testing reuses the gitignored `.agents/studi-qa/profile` after one human onboarding (Clerk, Codex, school sign-in) in that window. Do not point QA at the everyday Electron `userData`. Persistent QA must not sign out. Playwright drives Studi chrome; Pi owns the school guest pane. Isolated Playwright cannot finish OpenAI device authorization. Reuse `.agents/studi-qa/codex-auth` locally, or the Cursor Runtime Secret `STUDI_QA_CODEX_AUTH` for cloud and remote agents. If a code still appears, the user enters it in a real browser. Never commit the token or put it on GitHub.
- First-run onboarding asks for the student's name, checks the active agent runtime, uses an onboarding-agent chat to collect the student's school platform or URL, opens a persistent embedded browser for each required sign-in, asks for an automatic scan schedule, runs a visible first browser scan, then opens the populated weekly dashboard.
- School passwords stay inside the embedded browser session. Do not add password fields to the React app or store school credentials in app state.
- The school onboarding agent owns human handoffs. It tells the student when to sign in, verifies the browser session after the student returns, scans classes and assignments, detects linked third-party systems such as Cengage WebAssign, Pearson, Gradescope, McGraw Hill Connect, and zyBooks, and asks the student to sign in to those too.
- Third-party course systems are discovered during the first full class-and-assignment scan, not from a one-page check immediately after school login. The scan pauses for each required sign-in handoff and then resumes.
- Scan progress must be evidence-backed. Never mark a course, assignment, linked system, or workflow step complete unless the browser actually verified it. A zero-result or partial scan must stay visibly incomplete and must never fall back to seeded demo assignments.
- The first successful scan creates a local, versioned school-scan workflow. Later manual and scheduled scans replay it, re-discover courses, preserve learned navigation, record coverage and failures, and incorporate student feedback such as missed courses or assignment types.
- The Electron main process owns scan scheduling and local workflow persistence; passwords, cookies, and page HTML must never be written into workflow files.
- Do not claim Pi runs the current agent loop unless the app actually creates a Pi `AgentSession`. The current prototype calls the local Codex CLI directly and reuses its cached ChatGPT or API-key authentication. Pi is installed as an optional future provider adapter.
- Keep the dashboard's cream paper, dark hand-drawn border, Shantell Sans headings, Nunito Sans body copy, and yellow, coral, mint, sky, pink, and lavender course colors across new screens.

- Keep the manager-led build loop proportionate. The implementer reads the existing package plan, deepens it only when code-level uncertainty requires it, writes the production code, and owns useful programmatic checks. The tester never adds automated tests or changes production code; it opens the current app and exercises the package like a user through the closest real boundary. - The current task acts as the build manager. Every package gets a fresh implementer, a user-like tester when a real app or external boundary exists, and one read-only reviewer. The tester reports observed behavior and the smallest reproduction without editing code or adding tests. The reviewer judges elegance, traceability, and maintainability rather than thoroughness. If testing fails, the reviewer diagnoses the failure and writes a focused, elegant repair brief. If the implementation already earns a good quality rating and the approved behavior works, accept it without another implementation pass. Only concrete failures or clearly costly code problems start another loop. Each verified package gets its own concise flow-based HTML conclusion before work moves to the next package.
- Starting after WP-06, create implementer, tester, and reviewer roles as separate user-visible Codex tasks rather than internal sub-agents. The manager coordinates them, waits for their reports, and keeps the package stop point unchanged.
- For user-like Electron testing, use Microsoft's official Playwright MCP through a loopback-only Electron CDP endpoint. Prefer accessibility snapshots and semantic interaction. Keep Studi's deterministic app-control receipts for durable state, restart, main-process, and policy checks. Use generic computer control only for OS-owned dialogs or native surfaces Playwright cannot reach.
- Keep implementation and verification tasteful. Prefer a small number of high-value modules and tests that cover real boundaries, recovery, and costly failure modes. Do not add repetitive tests or abstraction layers for line-count or coverage theater. Later packages may improve earlier-package code when the change removes duplication, strengthens a shared contract, or makes the runtime easier to maintain; retain the earlier package's gates and evidence.
- Treat code quality as a subtraction problem. Every new layer, abstraction, validator, recovery path, and test must support current approved behavior or a named current risk. Reviewers may block unnecessary indirection, duplicated ownership, or weak domain shapes, but theoretical hardening and imagined future coverage remain non-blocking follow-ups.
